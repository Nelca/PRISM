# PRISM ローカルデモ手順書

**対象読者:** このリポジトリを初めて動かす人(社内メンバー・デザインパートナー候補への説明担当者等)。
**前提:** ここで動かせるのは**架空企業「東海化成株式会社(架空)」のダミーデータ**によるデモです。実データではありません(`lib/demo/`参照)。実データでの検証は別途、デザインパートナーとの合意後に行います。
**最終更新:** 2026-08-16

---

## 0. このデモで何が確認できるか

M1(対象定義とLocate)からM8(記録・版管理基盤)まで、8つのモジュールが実際につながって動くことを確認できます。UIは「ホーム→①データと拠点の登録→②評価対象の絞り込み→③価値の算定と代表値の選択→④財務への影響→⑤対策と判定→⑥開示への反映」という一本道の6ステップに、業務フロー外の参照画面「記録(監査証跡)」を加えた構成です(旧版にあった`/intake`・`/decomposition`は`/sites`・`/valuation`にそれぞれ統合され、恒久リダイレクトになっています。詳細は`docs/uiux-revision-directive.md`)。

画面をひととおり辿ると、次のことを確認できます。

- 拠点データを投入すると、座標解決の失敗も含めて監査可能な形で記録される(M1)
- 感応度・影響しうる財務規模の大きい拠点だけが自動的に詳細評価に昇格する(M2)
- 貨幣化(M3)と、手法間の乖離が「精度の差ではなく範囲の違い」として分解される(M4)
- 自然調整後利益・自然債務が算出される(M5)
- ★判定(投資判断の承認基準をレンジがまたぐか)が確定する(M6)
- 過去の開示文言の根拠充足度が機械的に判定される(M7)。PDFからのAI抽出(段階1・2)も試せる(§5)
- すべての判断が監査証跡(AssumptionEntry)として自動記録される(M8)

roadmap/build-plan.md §7.1の[GATE](「1社分のデータでM1からM8が通る」)の**技術的な前提**を、実データではなくこのダミーデータで満たしていることのデモです。

## 1. セットアップ

**必要環境:** Node.js 20以上(本書の検証はNode.js 22.14.0で実施)。DB用にDocker(`docker compose`が動くこと)。

```bash
git clone <このリポジトリ>
cd prism
npm install
cp .env.example .env
```

### DBの起動とマイグレーション

**旧版と異なり、現在の画面はすべてDBに保存された最新の実行結果(run)を読みます**(`app/layout.tsx`のコメント参照)。DBなしではホーム画面すら開けないため、`npm run dev`の前に必ず以下を行ってください。

```bash
npm run db:up       # compose.yaml のPostgresをdocker composeで起動(ホスト側ポート5433)
npm run db:migrate   # スキーマ作成・prism_appロールの作成・権限設定
```

`.env`の`DATABASE_URL_MIGRATOR`(スキーマ所有者)・`DATABASE_URL`(アプリ用、台帳テーブルのUPDATE/DELETE権限なし)は`.env.example`の既定値のまま`compose.yaml`と対応しているため、値の変更は不要です。使い終わったら`npm run db:down`で停止できます。

## 2. 動作確認(自動テスト)

まず自動テストがすべて通ることを確認します。GATE検証(`lib/demo/gate-verification.test.ts`)もこの中に含まれます。

```bash
npm run typecheck   # 型検証
npm run lint        # ESLint
npm test            # DB不要のテスト(vitest run。81ファイル・416件、GATE検証含む)
```

DBを必要とするテスト(ファイル名が`*.db.test.ts`、5ファイル・27件)は`npm test`から除外されており、別コマンドで実行します(事前に上記§1のDB起動・マイグレーションが必要)。

```bash
npm run test:db
```

**本書更新時点で、`lib/db/decision-parameters.db.test.ts`の2件(承認閾値の段階的開示まわり)が失敗することを確認しています。** 新規にセットアップしたDBでも再現するため、テストの前提と`decision_count_entry`の計上ロジックの間の既存の不整合と見られます。本書が対象とするUI/UX修正(`docs/uiux-revision-directive.md`)のスコープ外であり、`packages/core`にも触れていないため、本書では既知の制限として記載するにとどめます。

`npm test`まで通れば、パイプライン全体(M1〜M8)がダミーデータで最後まで正しく動くことがコードレベルで保証されています。

## 3. ローカルでUIを起動する

```bash
npm run dev
```

ブラウザで `http://localhost:3000` を開きます(§1のDB起動・マイグレーションを済ませておくこと)。

**初回アクセス時、フォント(Shippori Mincho・Noto Sans JP・JetBrains Mono)の取得でネットワークアクセスが発生します。** 社内ネットワーク等でGoogle Fontsへのアクセスがブロックされている場合、フォント取得のみ失敗する可能性がありますが、画面自体の表示・機能には影響しません。

## 4. 画面ごとの見どころ

画面はすべて、ページ上部の細いバナー「デモデータ(架空企業)を表示中」でデモであることを常に示します。左のナビは業務順に「評価する(①〜③)/判断する(④〜⑤)/開示する(⑥)」の3グループ+参照画面「記録(監査証跡)」に並んでおり、番号や完了マークは常設ナビには出しません(工程の進捗表示はホームだけの役割です)。各画面のガイド文(タイトル横の「i」)は初回訪問時は開いた状態で表示され、閉じるとその画面用に記憶されます。各画面の末尾には前後の画面への文脈導線(「次:○○へ →」)があります。

### `/` ホーム — 現在地と次にやること

最初に開く画面です。3つのブロックで構成されます。**(a) 進捗:** ①〜⑥の6ステップが完了しているか(件数付き)を表示します。工程の可視化はこの画面だけが担い、常設ナビには出しません。**(b) 次にやること:** 代表値の未選択・承認閾値の未入力・結果の反映先が「弱」のまま・減損テスト前提への抵触・開示根拠不足など、人が判断しないと先に進めない項目を実データから導出して並べます(該当がなければ表示しません)。**(c) 分かったこと:** 「本社工場×取水量・水ストレスの試算は、算定方法によって年◯円〜◯百万円の幅がある」「四日市工場では判定が承認基準をまたがない」のように、算定・判定の結果から結論を先に書いた一文カードで示します。テンプレート+実データの機械的な埋め込みで、AIによる文章生成は行っていません。

### `/sites` — ① データと拠点の登録(M1:対象定義とLocate)

上段は登録手段(CSV3ファイル一括/1件ずつ追加のタブ)、記入するファイルと担当者の対応表(テンプレートは画面から直接ダウンロードできます)。中段は拠点一覧(5拠点:本社工場・金属加工工場・海外サプライヤー2社・四日市工場)と座標解決状態。**海外サプライヤーのうち1社(バングラデシュ)は住所しか登録されておらず、架空のジオコーディングが失敗する設定になっています。** この拠点が「取込時に除外された行」に理由付きで残っていること(黙って消えるのではなく記録が残る、という設計上重要なポイント)を確認してください。

### `/assessment` — ② 評価対象の絞り込み(M2:評価実行・深度可変)

冒頭に感応度が高い拠点の一覧(絞り込みの入力になる表)。続いて評価対象の一覧では、優先度を順位+横バーで示し、感応度・影響しうる財務規模・不確実性・開示必須性の4項目を「優先度の内訳」としてバーで内訳表示します(生の正規化スコアはtitle属性に退避)。行末に「優先度が上位◯%に入ったため、詳細評価の対象です」のような判定文がそのまま出ます。本社工場(水)と四日市工場(GHG)の2件が詳細評価に昇格し、金属加工工場は上位に入らず概算評価のみに留まっていることを確認してください。

### `/valuation` — ③ 価値の算定と代表値の選択(M3:貨幣化エンジン/M4:乖離分解)

旧版の`/valuation`と`/decomposition`を統合した画面です。上から(1)算定対象と適用手法の一覧表、(2)試算の幅(フットボールチャート、1回だけ)、(3)差が生じる理由(ウォーターフォール+読み下し文)、(4)幅が違う理由、(5)**投資判断に使う代表値の選択(この画面の出口となる必須操作。推奨値は表示されません。変更時は理由の入力が必須です)**、(6)前年度手法との比較、の順に並びます。交換価値グループと厚生価値グループが「比較不能」として明示的に分離されている点(構想書8.2の規律、「投資判断には使用しません」の明示)を確認してください。金額は表ごとに単位(百万円/億円)を揃えて表示し、正確な値はホバーで確認できます。トルネード図・除外項目は「詳しく見る」に折りたたまれています。

### `/financial-bridge` — ④ 財務への影響(M5:財務接続)

選んだ代表値をもとにした自然調整後利益のウォーターフォール、期待損失(未内部化コスト・自然債務)、社会全体への影響(開示専用の参考値。利益の試算には反映しないことを明示)、比較先(格付・資本コストへの定性的な参考情報)を拠点ごとに表示します。すべての金額表示に「非GAAP指標」ラベルと「監査済み財務諸表の数値ではありません」の注記が付いていることを確認してください。末尾の「重要な論点」カードは、ホームの「次にやること」と同じ関数(`lib/pipeline/open-tasks.ts`)から導出しています。

### `/decision` — ⑤ 対策と判定(M6:意思決定注入)

拠点ごとに(1)判定結果を大きく先頭に(「承認基準をまたがない」+その意味の一文)、(2)対策案の比較(表→散布図の順。散布図は「投資1億円あたりの投資対効果(NPV)」「投資1億円あたりの回避物理量」で軸を揃えています)、(3)この結果の反映先、の順に並びます。前提が変わった判定(GAP-20)のアラートは判定結果カードの直下に出ます。過去の判定を書き換えることはせず、見直しが必要かどうかを伝えるだけです。旧版で末尾に同居していた課金明細(判定件数)は「記録」画面に移設されています。

### `/disclosure` — ⑥ 開示への反映(M7:開示生成と整合検証)

冒頭の「PDFから主張を抽出する」フォームは、統合報告書等のPDFをアップロードするとAI(Anthropic Claude API)が主張(claim)を抽出します。**抽出のみがAIの役割で、根拠充足の判定(下のGapFinding)はルールベースの構造化フィールド照合のみで行われ、AIは使われていません。** 各claimカードは、根拠となる算定結果との整合性の判定結果(根拠充足/G1〜G6のいずれか)と、根拠が不足している場合の3つの対応(記載を弱める・根拠を追加取得する・判断の理由を記録する)を示します。末尾の「開示文の下書き」は登録済みのレコードから固定テンプレート+機械的な数値埋め込みで組み立てたもので、こちらもAIによる文章生成は行っていません。

### `/ledger` — 記録(監査証跡、M8:記録・版管理基盤)

業務フローの外にある参照画面(左ナビの下部に分離)。先頭は人が読める2表(変更履歴=誰がいつ何を選び、なぜか/係数・パラメータの版=どの版がいつから有効か)。続いて判定件数(従量課金の根拠。⑤から移設)。ハッシュ類・レコード単位の再計算照合・旧版パラメータでの再計算は「技術的な検証情報」として折りたたまれています。**この画面がPRISMの「継続理由」(design-rationale-log D-04)そのものです** — 派手ではありませんが、監査・保証(ISSA 5000等)への耐性を支える部分です。

## 5. 出力APIの確認

```bash
curl http://localhost:3000/api/pipeline-result -H "x-api-key: <PRISM_API_KEYに設定した値>" | jq .
```

UIと同じパイプライン結果をJSONで取得できます。将来のERP埋め込み(構想書10.4)に備えた最小限の実装です。**`.env`の`PRISM_API_KEY`を設定していない場合、このAPIは503を返して停止します**(未設定を「認証なしで全開放」とは解釈しない、GAP-16のfail-closed設計)。`x-api-key`ヘッダが一致しない場合は401です。返るのは既定テナント(`PRISM_DEFAULT_TENANT_ID`)の最新runのみで、テナントをまたぐ参照はできません。

PDFからの主張抽出(§4 `/disclosure`)を試す場合は、別途`ANTHROPIC_API_KEY`環境変数の設定が必要です(`.env.example`には含まれていないため、使う場合は自分で追加してください)。未設定のまま抽出フォームを使うとエラーになりますが、画面の他の機能には影響しません。

## 6. ダミーデータについての注意事項

- **架空のデータです。** 数値(取水量・単価・財務データ)はデモ用に作成した設定値で、実在の企業・数値ではありません。
- **モンテカルロ乱数はデモ専用にシード固定されています**(`lib/demo/run-demo-pipeline.ts`)。同じ入力であれば毎回同じ数値が表示されます。これはデモの一貫性のための措置で、`packages/core`本体(本番相当のロジック)は変更していません。実際の計算では乱数は毎回変わります。
- **認証・テナント分離は未実装です。** ローカルで動かす前提の現段階の判断です(design-rationale-log D-102)。DBの永続化は導入済みですが(§1)、ログインや複数テナントの切り替えUIはありません。

## 7. ダミーデータを差し替えたい場合

`lib/demo/company.ts`が架空企業のデータ一式(拠点・感応度判定用のレイヤ照会・貨幣化の設定・対策・開示claim)を持っています。ここを書き換えると、UI・出力API・GATE検証テストすべてに反映されます。ただし現在の画面はDBに保存された最新runを読むため、変更後にUIへ反映するには一度既存のrunをクリアするか(`npm run db:down && npm run db:up && npm run db:migrate`でDBを作り直す)、新しいテナントIDで開く必要があります。

実データへの本格的な差し替え(デザインパートナーの実データ投入)は、`/sites`画面から記入テンプレート(CSV3ファイル一括)または1件ずつ追加する経路が用意されています(`lib/intake/`)。記入者の対応表・記入例のダウンロードリンクは画面内にあります。詳細は`docs/data-intake-guide.md`。

## 8. 既知の制限事項

- 認証・テナント分離なし(§6参照)
- `npm run test:db`に2件の既知の失敗があり、UI/UX修正のスコープ外(§2参照)
- 出力APIはGETのみ(閲覧専用)。PDF抽出フォーム経由のPOSTアクションを除き、UIからの操作はすべてサーバーアクション経由でDBに追記される
- 実際のジオコーディング・WDPA/IBAT/ENCORE等の外部データ照会は行っていない(いずれも注入可能なインターフェースとして実装されており、実データ接続時に外部サービス呼び出しを差し込む設計)
- PDF抽出(M7段階1・2)のみAIを使用する。判定(段階3・4)・「分かったこと」・開示下書きはいずれも固定テンプレート+実データの機械的な埋め込みで、AIによる文章生成ではない
