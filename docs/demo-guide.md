# PRISM ローカルデモ手順書

**対象読者:** このリポジトリを初めて動かす人(社内メンバー・デザインパートナー候補への説明担当者等)。
**前提:** ここで動かせるのは**架空企業「東海化成株式会社(架空)」のダミーデータ**によるデモです。実データではありません(`lib/demo/`参照)。実データでの検証は別途、デザインパートナーとの合意後に行います。
**最終更新:** 2026-08-03

---

## 0. このデモで何が確認できるか

M1(対象定義とLocate)からM8(記録・版管理基盤)まで、8つのモジュールが実際につながって動くことを確認できます。具体的には:

- 拠点データを投入すると、座標解決の失敗も含めて監査可能な形で記録される(M1)
- 感応度・財務エクスポージャの大きい拠点だけが自動的に深掘り評価に昇格する(M2)
- 貨幣化(M3)と、手法間の乖離が「精度の差ではなく範囲の違い」として分解される(M4)
- 自然調整後利益・自然債務が算出される(M5)
- ★判定(投資判断の閾値をレンジがまたぐか)が確定する(M6)
- 過去の開示文言の根拠充足度が機械的に判定される(M7)
- すべての判断が監査証跡(AssumptionEntry)として自動記録される(M8)

build-plan §7.1の[GATE](「1社分のデータでM1からM8が通る」)の**技術的な前提**を、実データではなくこのダミーデータで満たしていることのデモです。

## 1. セットアップ

**必要環境:** Node.js 20以上(このリポジトリの検証はNode.js 24で実施)。

```bash
git clone <このリポジトリ>
cd prism
npm install
```

## 3. ローカルでUIを起動する

```bash
npm run dev
```

ブラウザで `http://localhost:3000` を開きます。

**初回アクセス時、フォント(IBM Plex Mono等)の取得でネットワークアクセスが発生します。** 社内ネットワーク等でGoogle Fontsへのアクセスがブロックされている場合、フォント取得のみ失敗する可能性がありますが、画面自体の表示・機能には影響しません。

## 4. 画面ごとの見どころ

上部のナビゲーションから各画面を行き来できます。

### `/` 概要

拠点数・除外拠点数・深掘り昇格件数・開示ギャップ検出件数のサマリーと、★判定・AssumptionEntry件数を表示します。まずここで全体像を掴んでください。

### `/sites` — M1(対象定義とLocate)

拠点一覧(本社工場・金属加工工場・海外サプライヤーの3拠点)と、拠点×カテゴリごとのMaterialIssue(感応度スコア)を表示します。**海外サプライヤーは住所しか登録されておらず、架空のジオコーディングが失敗する設定になっています。** この拠点が「除外」として、除外理由付きで監査可能な形に記録されていることを確認してください(黙って消えるのではなく、記録が残る、という設計上重要なポイントです)。

### `/assessment` — M2(評価実行・深度可測)

各MaterialIssueの優先度算定の内訳(感応度・財務エクスポージャ・不確実性・開示必須性とその正規化スコア)と、深掘り評価に昇格したかどうかを表示します。本社工場(感応度・財務エクスポージャとも最大)だけが深掘りに昇格し、金属加工工場は「上位20%に入らなかった」という除外理由とともにスクリーニングのみで留まっていることを確認してください。

### `/valuation` — M3(貨幣化エンジン)/ M4(乖離分解)

深掘り評価に昇格した本社工場について、代替費用法・LIME3・IFVI(4つの内訳)、合計6本のValuationRecordが生成されていることを確認できます。交換価値グループと厚生価値グループが「比較不能」として明示的に分離されている点(構想書8.2の規律)、乖離分解の読み下し文(どの要因が寄与し、どの要因が「分解不能」として残差に落ちたか)を見てください。

### `/decision` — M6(意思決定注入)/ M5(財務接続)

★判定(承認閾値に対しレンジがまたぐか)、自然調整後NPV、自然調整後利益のウォーターフォール、比較先(格付・資本コストへの定性的な参考情報)を表示します。すべての金額表示に「非GAAP指標」ラベルが付いていることを確認してください。

### `/disclosure` — M7(開示生成と整合検証)

架空の統合報告書の主張文(「2030年までに本社工場の水使用量を20%削減」)に対し、根拠となるValuationRecordとの整合性が機械的に判定された結果(GapFinding)を表示します。判定にAIは一切使われていません(ルールベースの構造化フィールド照合のみ)。

### `/ledger` — M8(記録・版管理基盤)

ここまでの全ステップで自動生成されたAssumptionEntry(誰が・いつ・どの判断を・どの根拠で下したかの監査証跡)の一覧と、パイプライン全体の版情報から算出されたRecalculationHashを表示します。**この画面がPRISMの「継続理由」(D-04)そのものです** — 派手ではありませんが、監査・保証(ISSA 5000等)への耐性を支える部分です。

## 6. ダミーデータについての注意事項

- **架空のデータです。** 数値(取水量・単価・財務データ)はデモ用に作成した設定値で、実在の企業・数値ではありません。
- **モンテカルロ乱数はデモ専用にシード固定されています**(`lib/demo/run-demo-pipeline.ts`)。ページを再読み込みしても毎回同じ数値が表示されます。これはデモの一貫性のための措置で、`packages/core`本体(本番相当のロジック)は変更していません。実際の計算では乱数は毎回変わります。
- **認証・テナント分離は未実装です。** ローカルで動かす前提の現段階の判断です(design-rationale-log D-102)。

---

## 7. ダミーデータを差し替えたい場合

`lib/demo/company.ts`が架空企業のデータ一式(拠点・感応度判定用のレイヤ照会・貨幣化の設定・対策・開示claim)を持っています。ここを書き換えると、UI・出力API・GATE検証テストすべてに反映されます。

実データへの本格的な差し替え(デザインパートナーの実データ投入)は、`lib/demo/company.ts`と同じ形のデータ投入経路を別途用意する想定です(現時点では未着手)。

## 8. 既知の制限事項

- 認証・テナント分離なし(§6参照)
- フットボールチャート等の高度な可視化はなく、表形式の表示に留めている
- 出力APIはGETのみ(閲覧専用)
- 実際のジオコーディング・WDPA/IBAT/ENCORE等の外部データ照会・PDF抽出・LLMによる主張分類は行っていない(いずれも注入可能なインターフェースとして実装されており、実データ接続時に外部サービス呼び出しを差し込む設計)
