# PRISM ローカルデモ手順書

**対象読者:** このリポジトリを初めて動かす人(社内メンバー・デザインパートナー候補への説明担当者等)。
**前提:** ここで動かせるのは**架空企業「東海化成株式会社(架空)」のダミーデータ**によるデモです。実データではありません(`lib/demo/`参照)。実データでの検証は別途、デザインパートナーとの合意後に行います。
**最終更新:** 2026-10-04(2026-10-03の視覚化リデザインを反映)

## 0. このデモで何が確認できるか

M1(対象定義とLocate)からM8(記録・版管理基盤)まで、8つのモジュールが実際につながって動くことを確認できます。UIは、左ナビの3グループ「データを評価する(環境・資源の統合管理/拠点とデータ/評価対象/価値算定)→経営判断につなげる(財務影響/対策と判定)→社内外に伝える(開示)」に、管理「記録」とサポート「PRISMとは・使い方」を加えた構成です。2026年10月の視覚化リデザインで、各画面の冒頭に現在の状態を要約するKPIタイル、完了・進行中・要対応・保留を色付きドットで示す状態バッジ、比率の分割バー、拠点×カテゴリのヒートマップ、判定結果の範囲バー(承認ラインの破線付き)、ホームの6工程ステッパーが加わり、ナビと見出しにはアイコンが付きました(部品の一覧は`docs/uiux-visual-refresh-2026-10.md`)。計算・判定・開示の処理はこの改修で変わっていません。

画面をひととおり辿ると、次のことを確認できます。

- 拠点データを投入すると、座標解決の失敗も含めて監査可能な形で記録される(M1)
- 感応度・影響しうる財務規模の大きい拠点だけが自動的に詳細評価に昇格する(M2)
- 貨幣化(M3)と、手法間の乖離が「精度の差ではなく範囲の違い」として分解される(M4)
- 自然調整後利益・自然債務が算出される(M5)
- ★判定(投資判断の承認基準をレンジがまたぐか)が確定する(M6)
- 過去の開示文言の根拠充足度が機械的に判定される(M7)。PDFからのAI抽出(段階1・2)も試せる(§5)
- すべての判断が監査証跡(AssumptionEntry)として自動記録される(M8)

roadmap/build-plan.md §7.1の[GATE](「1社分のデータでM1からM8が通る」)の**技術的な前提**を、実データではなくこのダミーデータで満たしていることのデモです。

## 1. セットアップ

**必要環境:** Node.js 20以上(本書の検証はNode.js 22.14.0で実施)。DB用にDocker(`docker compose`が動くこと)。

```bash
git clone <このリポジトリ>
cd prism
npm install
cp .env.example .env
```

### DBの起動とマイグレーション

**旧版と異なり、現在の画面はすべてDBに保存された最新の実行結果(run)を読みます**(`app/layout.tsx`のコメント参照)。DBなしではホーム画面すら開けないため、`npm run dev`の前に必ず以下を行ってください。

```bash
npm run db:up       # compose.yaml のPostgresをdocker composeで起動(ホスト側ポート5433)
npm run db:migrate   # スキーマ作成・prism_appロールの作成・権限設定
```

`.env`の`DATABASE_URL_MIGRATOR`(スキーマ所有者)・`DATABASE_URL`(アプリ用、台帳テーブルのUPDATE/DELETE権限なし)は`.env.example`の既定値のまま`compose.yaml`と対応しているため、値の変更は不要です。使い終わったら`npm run db:down`で停止できます。

## 4. 画面ごとの見どころ

画面はすべて、ページ上部の細いバナー「デモワークスペース 架空企業のデータで操作を試せます」でデモであることを常に示します。左のナビは業務順の3グループ「データを評価する/経営判断につなげる/社内外に伝える」+管理「記録」+サポート「PRISMとは・使い方」に並び、各項目に工程アイコンが付きます。未完了の判断がある画面には金色のドットが出ます。番号や完了マークは常設ナビには出しません(工程の進捗表示はホームのステッパーだけの役割です)。各画面のタイトル横の「使い方」を押すと、その画面でやること・手順の案内が開きます。各画面の末尾には前後の画面への文脈導線(「次:○○へ →」)があります。

状態を示す色は全画面で共通です: **緑=完了・達成・承認ラインをまたがない**、**青=進行中・詳細評価の対象**、**赤茶=要対応・未達・承認ラインをまたぐ**、**金=保留(承認ライン未入力など、仮置きせずに判定していない状態)**。色だけに意味を持たせず、必ず文言と数値を併記しています。

### `/` ダッシュボード — 製品の価値、次の操作、全体の流れ、結果

最初に開く画面です。上から順に、**(a) 導入ブロック:** 「自然への影響を、経営の判断材料に。」の見出しと、「デモの算定結果を見る」「自分の拠点を登録する」の入口。その下に「手元の環境データを登録 → 金額の幅と差の理由を確認 → 投資判断と開示に活用」の3段を、工程アイコン付きの機能カードで示します(×で閉じると記憶され、「PRISMとはを再表示」で戻せます)。**(b) 資源・生態系もまとめて管理:** 環境・資源の統合管理(`/portfolio`)への入口。**(c) 評価を進める:** 要対応件数と「次の操作」(代表値の未選択など、人が判断しないと先に進めない項目の先頭1件。`lib/pipeline/open-tasks.ts`から導出)。**(d) 全体の流れ:** 6工程のステッパー(完了=青塗り、要対応=赤茶、進行中=青枠)と、工程ごとの状態バッジ+要対応項目へのリンク。**(e) 登録データから得られた結果:** 登録データ5拠点 → 評価対象(4/11課題の分割バー) → 価値の算定8課題 → 財務への影響(自然債務合計1.7億円) → 対策と判定(2/2拠点) → 開示への反映(0/1件)の6枚のKPIタイルと、拠点別の財務影響表(利益への影響バー、判定バッジ、減損リスク)、工程別の主な結果カード。結果の文は固定テンプレート+実データの機械的な埋め込みで、AIによる文章生成は行っていません。

### `/portfolio` — 環境・資源の統合管理(物理目標の横断管理)

GHG・水・汚染物質・廃棄物・土地利用に加え、生物資源・鉱物資源・生態系の状態を、拠点を横断して目標と比較する画面です(2026年9月追加)。上段の4枚のタイル「管理対象22件/確認・対応が必要14件/物理目標が未達8件/対応期限を超過1件」は進捗リング付きで、押すと一覧がその条件に絞り込まれます。**拠点別のカバー状況**は拠点×カテゴリのヒートマップで、件数が多いセルほど濃い青、**未登録のセルは斜線**で「0件」と区別します(未登録は影響ゼロを意味しない、という規律の表示)。セルを押しても絞り込めます。一覧では、状態を色付きバッジ(目標未達=赤茶、算定済み=緑、未算定・代表値未選択=金)、実測と目標を1本のバー(目標の目盛り付き)、対応期限の超過をバッジで示します。行の「確認・更新」から指標の詳細(`/portfolio/[targetId]`)に入ると、実測・目標・差・期限の4タイルと目標バーが先頭に出ます。CSV一括取込(`/portfolio/import`)・指標の追加(`/portfolio/new`)も右上から開けます。

### `/sites` — 拠点とデータ(M1:対象定義とLocate)

上段左は「登録・取込」の4枚の機能カード(拠点データを登録する/PRTR排出量を取り込む/廃棄物データを取り込む/土地利用データを取り込む。それぞれカテゴリのアイコン付き)、右は入力ファイル(参考)の対応表(テンプレートは画面から直接ダウンロードできます)。中段は拠点一覧(5拠点:本社工場・金属加工工場・海外サプライヤー2社・四日市工場)で、「座標解決」列が緑の「座標あり」/赤茶の「未解決」バッジになっています。**海外サプライヤーのうち1社(繊維)は住所しか登録されておらず、架空のジオコーディングが失敗する設定です。** この拠点が「取込時に除外された行」に理由付きで残ること(黙って消えるのではなく記録が残る、という設計上重要なポイント)を確認してください。

PRTRは本紙・別紙・他業種のCP932 TXTと拠点crosswalkのUTF-8 CSVの4ファイル、廃棄物・土地利用はUTF-8 CSVで、サンプルを各取込画面からダウンロードできます。PRTR→廃棄物→土地利用の順で登録すると、廃棄物サンプルのPRTR移動量リンクも検証できます。詳しい値とファイル一覧は`docs/data/category-expansion-acquisition.md` §1.2を参照してください。

### `/assessment` — 評価対象の絞り込み(M2:評価実行・深度可変)

冒頭の3枚のタイル「評価対象11件/詳細評価8件/対象外7件」で全体像をつかみます。評価対象の一覧では、優先度を順位+横バーで、感応度(自然との関わり)・財務・不確実性・開示の4項目を**1本の積み上げバー**で示します(凡例は表の上に1回。生の値はバーのツールチップに退避)。「評価の深さ」列は現在値のバッジ(詳細評価=青/概算評価=灰/対象外=金)の下に、概算⇄詳細の切替ボタンがあります。行末の「理由」に「手動で詳細評価の対象に指定されています」「優先度が上位20%に入らなかったため、概算評価に留まっています」のような判定文がそのまま出ます。課題名を押すと詳細(`/assessment/[issueId]`)に入り、感応度の基準充足を「1/3基準」の分割バーで確認できます。

### `/valuation` — 価値の算定(M3:貨幣化エンジン/M4:乖離分解)

冒頭に要対応の帯(代表値が未選択:2件など)、続いて「詳細評価の対象8件」と「代表値の選択0/2」(進捗リング)のタイル。課題はコンボボックス(「本社工場 × 廃棄物・資源循環 全8件」)で切り替えます。選んだ課題について、上から(1)算定の対象(自然との関わり1/3、物理量、適用中の算定方法数)、(2)次の判断(代表値の選択または企業交換価値の財務反映の確認。**この画面の出口となる必須操作で、推奨値は表示されません。変更時は理由の入力が必須です**)、(3)財務ブリッジへ渡す企業交換価値、(4)入力・算定カバレッジ(算定済み/未算定、入力元、係数セットの版、ライセンス状態)、(5)**適用している算定方法**の表(価値の性質=交換価値/厚生価値のタグ、確からしさ=Tier A/B/C・直接算定のバッジ、中心値、**幅(P5〜P95)を数値と帯で表示**。同じ表の帯は軸を共通にしてあり、行同士で幅を比べられます)、(6)入力行別の算定明細、(7)「この画面内で詳細分析を確認する」(折りたたみ。フットボールチャート・ウォーターフォール・トルネード図)、(8)まだ代表値を選んでいない課題への導線、の順に並びます。交換価値グループと厚生価値グループが「比較不能」として明示的に分離されている点(構想書8.2の規律)を確認してください。金額は表ごとに単位(百万円/億円)を揃え、正確な値はホバーで確認できます。手法比較の専用画面は`/analysis`(結論の3タイル、寄与分解の積み上げバー、ウォーターフォール)、根拠は`/evidence`です。

### `/financial-bridge` — 財務への影響(M5:財務接続)

冒頭の3枚のタイル「自然債務合計1.7億円/減損リスク拠点数1拠点(1/2件の分割バー)/利益影響の最大(絶対値)-15.6% 四日市工場」で、どの拠点を先に見るべきかが分かります。続いて、企業財務へ接続していない評価結果(厚生価値のみの追加カテゴリ。利益の試算には反映しないことを明示)、企業全体の財務データ、拠点サマリー(利益への影響を左右バー、自然債務、減損リスクを「範囲内」=緑/「見直しが必要」=赤茶のバッジ)。行の「詳細」で拠点別(`/financial-bridge/[siteId]`)に入ると、自然コスト反映後の営業利益のウォーターフォール、報告営業利益・自然調整後営業利益・自然債務の3タイル、期待損失の内訳が並びます。すべての金額に「社内試算値(決算数値ではありません)」のラベルが付いていることを確認してください。末尾の「財務試算の前提で確認すること」は、ホームの「次の操作」と同じ関数(`lib/pipeline/open-tasks.ts`)から導出しています。

### `/decision` — 対策と判定(M6:意思決定注入)

冒頭の3枚のタイル「判定確定2/2拠点(分割バー)/承認ライン超過件数0件/未反映件数2件」。続いて資源対策の投資比較、要対応の帯、「社会的厚生価値は投資判定に加算しません」の明示、拠点サマリー(判定バッジ、選択中の対策、反映先、残タスク)。行の「詳細」で拠点別(`/decision/[siteId]`)に入ると、**判定結果**カードに判定バッジ(「承認ラインをまたがない」=緑)と、**調整後NPVのP5〜P95の帯+承認ラインの破線**が出ます。帯が線をまたげば赤茶、またがなければ緑、承認ラインが未入力なら線を描かず金色の帯で「保留」を示します(仮の基準で結論を出さない規律)。「対策案を選ぶ」の表では、投資額を候補間で比べる分割バー、投資価値(NPV)を同じ軸の帯で示し、「この案で判定」で切り替えられます。「この結果の反映先」は稟議書への参考記載/NPV判定式への組み込み/拠点予算への反映/調達契約の更新条件の4択で、選択・記録しても外部システムは更新されません。「比較分析」タブ(`/decision/[siteId]/analysis`)には散布図(投資1億円あたりの投資対効果と回避物理量)があります。前提が変わった判定のアラートは判定結果カードの直下に出ます。

### `/disclosure` — 開示への反映(M7:開示生成と整合検証)

冒頭の3枚の機能カード「指摘(根拠との不一致に対応)/PDF取込(開示文から主張を抽出)/下書き(登録済みレコードから作成)」が各サブ画面への入口です。続いて要対応の帯(根拠不足の開示文言:1件)、「根拠確認の進捗0/1件」のタイル(進捗リング)、追加カテゴリの算定範囲と除外、指摘の一覧(種別=G1〜G6のバッジ、一致した根拠の件数、対応状況=未対応は赤茶)。指摘の「詳細」(`/disclosure/[findingId]`)では、根拠となる算定結果との整合性の判定と、根拠が不足している場合の3つの対応(記載内容を弱める・詳細評価に追加する・判断の理由を記録する)を選びます。PDF取込(`/disclosure/intake`)はAI(Anthropic Claude API)で主張(claim)を抽出しますが、**抽出のみがAIの役割で、根拠充足の判定はルールベースの構造化フィールド照合のみで行われ、AIは使われていません。** 下書き(`/disclosure/draft`)は登録済みレコードから固定テンプレート+機械的な数値埋め込みで組み立てたもので、こちらもAIによる文章生成は行っていません。

### `/ledger` — 記録(監査証跡、M8:記録・版管理基盤)

業務フローの外にある参照画面(左ナビの「管理」に分離)。入口は4枚の機能カード「変更履歴(担当・日時・変更内容)/入力・係数(算定根拠を照合)/版と再計算(現在版と旧版を比較)/判定件数(従量課金の根拠)」で、各サブ画面(`/ledger/history`・`/ledger/inputs`・`/ledger/parameter-versions`・`/ledger/billing`)に分かれています。変更履歴は人が読める表(誰がいつ何を選び、なぜか)、版と再計算は係数・ルールごとの版と有効開始日(有効=緑のバッジ)、判定件数は確定した判定の一覧(判定バッジ付き)。ハッシュ類・再計算照合は「技術的な検証情報」として折りたたまれています。**この画面がPRISMの「継続理由」(design-rationale-log D-04)そのものです** — 派手ではありませんが、監査・保証(ISSA 5000等)への耐性を支える部分です。

### `/guide` — PRISMとは・使い方

ワークフロー外の説明画面。何をするプロダクトか、6工程のステッパー、資源・生態系を含む目標管理、得られる3つの成果物(投資判断への判定/開示の記載と根拠/監査証跡)の機能カード、使い方の流れ(入れるもの・得られるもの)、年間サイクル(Q1〜Q4)、数字を信頼できるものにするための5つの決まりごとが並びます。初見の相手にはホームの次にこの画面を見せると、全体像を2分で説明できます。

### 画面で見せる場合の順番(5分の目安)

1. `/`:導入ブロックと「全体の流れ」のステッパーで、6工程と現在地(要対応が赤茶で2工程)を見せる。

## 5. 出力APIの確認

```bash
curl http://localhost:3000/api/pipeline-result -H "x-api-key: <PRISM_API_KEYに設定した値>" | jq .
```

UIと同じパイプライン結果をJSONで取得できます。将来のERP埋め込み(構想書10.4)に備えた最小限の実装です。**`.env`の`PRISM_API_KEY`を設定していない場合、このAPIは503を返して停止します**(未設定を「認証なしで全開放」とは解釈しない、GAP-16のfail-closed設計)。`x-api-key`ヘッダが一致しない場合は401です。返るのは既定テナント(`PRISM_DEFAULT_TENANT_ID`)の最新runのみで、テナントをまたぐ参照はできません。

PDFからの主張抽出(§4 `/disclosure`)を試す場合は、別途`ANTHROPIC_API_KEY`環境変数の設定が必要です(`.env.example`には含まれていないため、使う場合は自分で追加してください)。未設定のまま抽出フォームを使うとエラーになりますが、画面の他の機能には影響しません。

## 6. ダミーデータについての注意事項

- **架空のデータです。** 数値(取水量・単価・財務データ)はデモ用に作成した設定値で、実在の企業・数値ではありません。
- **PRTR・廃棄物・土地利用も架空値です。** 追加カテゴリの有効な入力バッチが一件もない場合だけデモrunへ入り、顧客入力が有効になった後は混在しません。配布ファイルと同じ値は`lib/demo/category-expansion-data.ts`にあります。
- **モンテカルロ乱数はデモ専用にシード固定されています**(`lib/demo/run-demo-pipeline.ts`)。同じ入力であれば毎回同じ数値が表示されます。これはデモの一貫性のための措置で、`packages/core`本体(本番相当のロジック)は変更していません。実際の計算では乱数は毎回変わります。
- **認証・テナント分離は未実装です。** ローカルで動かす前提の現段階の判断です(design-rationale-log D-102)。DBの永続化は導入済みですが(§1)、ログインや複数テナントの切り替えUIはありません。

## 7. ダミーデータを差し替えたい場合

`lib/demo/company.ts`が架空企業のデータ一式(拠点・感応度判定用のレイヤ照会・貨幣化の設定・対策・開示claim)を持っています。ここを書き換えると、UI・出力API・GATE検証テストすべてに反映されます。ただし現在の画面はDBに保存された最新runを読むため、変更後にUIへ反映するには一度既存のrunをクリアするか(`npm run db:down && npm run db:up && npm run db:migrate`でDBを作り直す)、新しいテナントIDで開く必要があります。

実データへの本格的な差し替え(デザインパートナーの実データ投入)は、`/sites`画面から記入テンプレート(CSV3ファイル一括)または1件ずつ追加する経路が用意されています(`lib/intake/`)。記入者の対応表・記入例のダウンロードリンクは画面内にあります。詳細は`docs/data-intake-guide.md`。

## 8. 既知の制限事項

- 認証・テナント分離なし(§6参照)
- `npm run lint`(全体)は`tools/promotion/*.cjs`の既存エラーで失敗する。アプリ本体(`app`・`lib`)はエラー0(§2参照)
- 出力APIはGETのみ(閲覧専用)。PDF抽出フォーム経由のPOSTアクションを除き、UIからの操作はすべてサーバーアクション経由でDBに追記される
- 実際のジオコーディング・WDPA/IBAT/ENCORE等の外部データ照会は行っていない(いずれも注入可能なインターフェースとして実装されており、実データ接続時に外部サービス呼び出しを差し込む設計)
- PDF抽出(M7段階1・2)のみAIを使用する。判定(段階3・4)・「分かったこと」・開示下書きはいずれも固定テンプレート+実データの機械的な埋め込みで、AIによる文章生成ではない
