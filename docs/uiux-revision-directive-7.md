# PRISM UI/UX修正指示書 第7版（初見理解の改善）

**作成日:** 2026-09-01
**位置づけ:** 現在の業務プロダクトを、初めて見る人にも「何ができ、なぜ役立つか」がすぐ伝わるようにするための、小規模な情報設計・コピー改善である。後続予定のプロモーション向けデザイン／構造刷新とは分離する。
**制約:** `packages/core`、API、DB、データ導出、既存の主要業務フローは変更しない。既存の未コミット変更はユーザーの作業として扱い、上書き・巻き戻しをしない。git commitしない。

---

## 1. 背景と目的

現状のホームは、既存利用者が次の作業へ進むためのダッシュボードとして機能している。一方で、PRISMを知らない人には、次の点が画面上部だけでは伝わりにくい。

- どのデータを入力するプロダクトか
- そのデータを何に変換するのか
- その結果をどの業務で使えるのか
- 従来の環境データ管理と比べて何が嬉しいのか

今回の目的は、最初の数秒で「既存の環境データを、説明可能な財務判断・開示・監査用の情報へ変えるプロダクト」と理解できる状態にすることである。大きなヒーロー、画像、ブランド刷新、ナビゲーション再編、公開ランディングページ化は対象外とする。

---

## 2. ホームの常設オリエンテーション領域

### D-01 【P0】ホーム最上部に、閉じられる説明領域を初回表示する

既存の「次にやること」より上、ページコンテンツの最初にオリエンテーション領域を表示する。初回は表示し、右上の閉じるボタンから非表示にできるようにする。閉じた状態は `localStorage` の `prism:home-orientation-dismissed:v1` に保存し、同じブラウザでの再訪時も維持する。保存できない環境でも、そのセッション中は閉じた状態を維持する。

非表示後に説明を読み直す場合は、常設ナビゲーションの「PRISMとは・使い方」から `/guide` を開けるため、ホーム上に再表示ボタンは追加しない。説明を非表示にした場合も、ページにはスクリーンリーダー向けのh1「ダッシュボード」を残す。既存利用者のタスク導線を妨げないよう、情報量はこの指示書の範囲に留める。

表示するコピーは以下で**確定**とする。

| 要素 | 表示文言 |
|---|---|
| eyebrow | `PRISMとは` |
| h1 | `環境データを、投資判断・開示・監査に使える財務情報へ` |
| lead | `取水量・GHG排出量など、すでにある環境データを金額の幅に換算し、投資判断への影響、開示文と根拠、選択理由の記録までを一つの流れで扱います。` |
| CTA | `PRISMを2分で理解する →` |

CTAは `/guide` へ遷移するリンクとする。説明の表示中は価値命題を可視h1とし、非表示中はスクリーンリーダー専用の「ダッシュボード」をh1とする。どちらの状態でもページ内のh1は1つだけにする。

### D-02 【P0】入力から成果物までを、1行のフローで明示する

D-01のleadの直後に、順番付きリスト（`ol`）として次のフローを表示する。

`環境データ → 複数手法で金額換算 → 投資判断・開示・監査証跡`

矢印は装飾として扱い、読み上げ対象にはしない。フローは処理順を見せるためのものであり、クリックや新しい機能を追加してはならない。

### D-03 【P0】利用者の便益を3つ、短く具体的に示す

D-02の下に、非順序リスト（`ul`）として次の3項目を表示する。

- `手元のデータから始められる` — 新しい計測を始めずに着手できる
- `差の理由を説明できる` — 複数手法の結果差と理由を確認できる
- `同じ結果を繰り返し使える` — 投資判断、開示、監査対応に再利用できる

見出しと説明文の関係が視覚的にも読み上げでも分かるようにする。成果を過大に約束する表現や、未実装の自動化を示す表現は追加しない。

### D-04 【P1】ホームの既存業務導線を維持する

既存の「次にやること」、KPI、財務影響、進捗、主な結果について、順序、文言、データ導出ロジックを変更しない。今回の説明領域はそれらの前に追加するだけとする。

## 3. `/guide` と案内名称の統一

### D-05 【P0】案内ページを「PRISMとは・使い方」として統一する

`/guide` の見出し、metadata、AppShellの画面名、ナビゲーション表記を `PRISMとは・使い方` に統一する。

- ScreenLead: `何を入れると、どの業務で使える情報になるかを2分で確認できます`
- 冒頭説明は、入力から利用先までを説明する1段落へ圧縮する。
- 既存の「3成果物」「6工程」「年間サイクル」「信頼の規律」「最初の一歩」は維持する。

用語を変えるだけで、既存の案内ページにあるリンク、操作手順、データ内容を変えてはならない。

---

## 4. 実装・スタイルの制約

### D-06 【P1】専用クラスで、既存スタイルへの副作用を避ける

- 導入領域には専用のBEMクラスを追加する。未使用の `.home-hero` は競合するレスポンシブ指定があるため再利用しない。
- デスクトップではフローと便益を3列で読みやすく配置し、767px以下では1列に縦積みする。
- 固定高、横スクロール、画像、派手な装飾、新規ライブラリ・依存関係は追加しない。
- CTAは通常のリンクとしてキーボード操作可能にし、十分に分かるフォーカス状態を既存トークンに沿って提供する。
- 既存のデザインシステム、余白、文字サイズ、色のトークンを優先する。

## 5. 実施順序

1. `docs/uiux-revision-directive-7.md` と `docs/README.md` を更新し、目的・確定コピー・対象外・受入基準を記録する。
2. ホームのオリエンテーション領域と専用スタイルを実装する。
3. `/guide`、ナビゲーション、AppShellの案内名称を統一する。
4. 型・lint・テスト・ビルド・HTTPスモークを確認する。
5. 実装担当とは別のレビュー担当が、実画面だけを材料に初見レビューを行う。
6. 再レビューで不合格または条件付き評価になった項目は修正し、同じ条件で再確認する。

## 6. 検証と受入基準

### 技術確認

- `npm run typecheck`
- `npm run lint`
- `npm test`
- `npm run build`
- `/`、`/guide`、主要業務ルートのHTTPスモーク確認
- ブラウザで1440px、1024px、768px、390px相当を確認する。
  - 横方向のはみ出しがない
  - h1から既存タスクまでの視線順が自然である
  - モバイルで説明が1列に縦積みされる
  - CTAをキーボードで操作できる
  - ヘッダー、ナビゲーション、案内ページの名称が一致する

### 初見レビュー

実装を知らないレビュー担当者は、少なくとも次の問いに実画面だけで答える。

- **5秒:** ホーム上部だけで「既存の環境データを金額と判断材料へ変える製品」と説明できる。
- **30秒:** 手元のデータから始められること、手法差を説明できること、結果を投資・開示・監査で再利用できることが分かる。
- **2分:** `/guide`まで読むと、入力、金額換算、3成果物、最初の操作を説明できる。
- **既存利用者:** 「次にやること」と主要KPIへ迷わず到達でき、説明領域が業務を妨げない。

最終確認では、次の問いに明示的に回答する。

> このプロダクトを全く知らない人が見て、何ができてどういった点が嬉しいのかをすぐに理解できるようになっていますか？

回答が「いいえ」または条件付きの場合は、該当箇所を修正してから再レビューする。後続のプロモーション向け刷新を理由に、今回の最低限の理解可能性を先送りしてはならない。

---

## 7. 対象外

- 公開ランディングページの新設
- ブランド、ロゴ、画像、ビジュアル表現の刷新
- 大型ヒーローやアニメーションの追加
- 機能・API・DB・算定ロジックの変更
- ナビゲーション全体の再編
- 顧客説明・プロモーションのための大規模なコピー／構造変更

これらは、本指示書で現状のプロダクトを簡潔で分かりやすくした後のフェーズで検討する。
