## 0. 位置づけ

従来通り。M1〜M4が通ってから実装しても遅くない(build-plan §5.5)。

**MVP範囲:** 単一パイプラインで深度を引数に取る(スクリーニング/深掘り)、優先度算定、除外理由の記録(必須)。カテゴリは気候・水・汚染の3つ、深度2段階。

**完了条件:** 同一パイプラインで深度を切り替えられ、除外した項目とその理由が全件記録される。

## 1. 決定事項 D-1:パイプラインは「全件スクリーニング→優先度算定→高優先度のみ深掘り」の2段階とする

### 論点

優先度算定式(感応度+財務エクスポージャ+不確実性の大きさ+開示必須性)のうち、財務エクスポージャ・不確実性の大きさはM3(貨幣化エンジン)の出力に依存する。しかしパイプラインはM1→M2→M3の順であり、M2がM3の結果を必要とすると循環するように見える。

### 採用する設計

循環ではなく、**2段階の直列処理**として解決する。

```
1. 全MaterialIssueについて、まずスクリーニング深度で物理量を粗く見積もり(業種別ベンチマーク等)、
   M3のスクリーニングモード(M3 D-6:ESVD要約値・ティアC固定)まで一度通す
2. スクリーニング結果(ValuationRecordの中心値・分位点レンジ)から優先度を算定する(§2)
3. 優先度が閾値を超えたMaterialIssueのみ、深掘り深度で実際の測定データを使い、
   M3の深掘りモード(個別ESVDレコード照合等)を再度通す
```

**「単一パイプラインで深度を引数に取る」(build-plan)の解釈:** 同じMaterialIssueが同じコードパスを、まずスクリーニング深度、次に(昇格した場合のみ)深掘り深度で通る、という意味と解釈する。M2が独自にM3を呼び出す特別なロジックを持つわけではなく、M3自体が既に持つスクリーニング/深掘りの区分(M3 D-6)をそのまま使う。

**理由:** 新しいデータパイプラインを発明せず、M3が既に持つ深度区分をそのまま再利用する(design-rationale-log D-03・D-37と同じ「自前構築は基盤に限定する」原則)。

## 2. 決定事項 D-2:優先度算定式の各項は、既存の出力を再利用し、正規化して合算する

### 各項の定義

```typescript
interface PriorityScore {
  materialIssueId: string;
  sensitivity: number;        // M1のsensitivityScore(0〜5)をそのまま使う
  financialExposure: number;  // スクリーニング深度のValuationRecord中心値(交換価値)
  uncertaintyMagnitude: number;  // スクリーニング深度のquantileRangeの幅 log(P95/P5)
  disclosureRequirement: number;  // カテゴリ×現行規制の対応表(下記)
  normalizedScore: number;    // 4項を正規化して合算した最終値
}
```

| 項目 | 定義 | 出典・理由 |
|---|---|---|
| 感応度 | M1の`MaterialIssue.sensitivityScore`(0〜5)をそのまま使う | 新規計算しない。M1 D-2で既に確定済み |
| 財務エクスポージャ | スクリーニング深度で生成されたValuationRecordの中心値(交換価値グループ) | M3のスクリーニング出力を再利用。新しい財務データソースを要求しない |
| 不確実性の大きさ | スクリーニング深度のquantileRange(P5/P95)の対数比 `log(P95/P5)` | M3が既に算出する分位点をそのまま使う。「深掘りの価値は不確実性の縮小にある」(build-plan)という趣旨を、M3の既存出力でそのまま表現できる |
| 開示必須性 | カテゴリ別の現行規制状況に基づく対応表(気候=高、水・汚染=中、将来の自然カテゴリ全般=低、規制確定次第見直す) | 構想書のSSBJタイムライン(気候先行、自然は2029〜2031年見込み)から機械的に導出。恣意的な数値ではない |

### 正規化方法

4項目は単位が異なる(0〜5の整数、金額、対数比、カテゴリ由来の値)ため、単純合算する前に**同一バッチ内での百分位順位(0〜1)に正規化する。**

```
normalizedScore = percentileRank(sensitivity) + percentileRank(financialExposure)
                + percentileRank(uncertaintyMagnitude) + percentileRank(disclosureRequirement)
```

**理由:** build-plan の式は単純な加算(感応度+財務エクスポージャ+不確実性の大きさ+開示必須性)として書かれており、4項目に対する重み付けの記載はない。したがって等重みの単純合算とし、独自の重み付けは行わない(M1 D-2・design-rationale-log D-26と同じ「恣意的な重みを加えない」原則)。ただし単位が異なる4値をそのまま加算すると特定の項目(特に金額)が支配的になるため、**加算する前に同一バッチ内の相対順位に変換する。** これは加重ではなく単位を揃えるための正規化であり、build-planの式の趣旨(等重みの合算)を保ったまま実装可能にする処理。

### 具体例(2026-08-02追記)

同一バッチに4件のMaterialIssueがあるとする。

| MaterialIssue | 感応度(0-5) | 財務エクスポージャ(円) | 不確実性 log(P95/P5) | 開示必須性 |
|---|---|---|---|---|
| A | 4 | 8,000万 | 0.5 | 高(=3) |
| B | 2 | 5,000万 | 1.8 | 中(=2) |
| C | 5 | 1,200万 | 0.3 | 高(=3) |
| D | 1 | 200万 | 2.5 | 低(=1) |

これを4件の中での百分位順位(0〜1、値が大きいほど1に近い)に変換する。

| MaterialIssue | 感応度の順位 | 財務の順位 | 不確実性の順位 | 開示の順位 | 合計(normalizedScore) |
|---|---|---|---|---|---|
| A | 0.75 | 1.00 | 0.50 | 0.875 | **3.125** |
| B | 0.50 | 0.75 | 0.75 | 0.625 | 2.625 |
| C | 1.00 | 0.50 | 0.25 | 0.875 | **2.625** |
| D | 0.25 | 0.25 | 1.00 | 0.375 | 1.875 |

上位20%(§3)の閾値をこの4件の中で適用すると、最上位のAのみが深掘りに昇格する(4件中上位1件=25%に相当し、実運用ではもっと多い母集団の中で上位20%を取る)。**金額(財務エクスポージャ)の絶対値をそのまま合算していたら、Aが8,000万円という金額の大きさだけで支配的になっていたところ、順位に変換することで4項目が対等に扱われている。**

## 3. 決定事項 D-3:深掘りへの昇格は暫定的な閾値(上位20%)とし、手動での強制昇格も許可する

```
デフォルト: normalizedScoreが同一バッチの上位20%に入るMaterialIssueを深掘り深度に昇格する
手動上書き: ユーザーが特定のMaterialIssueを、優先度算定の結果によらず深掘り対象に指定できる
```

**「上位20%」は暫定値。** design-rationale-log D-26(M3のティア閾値)・M4のF-3/F-8と同じ扱いで、フェーズ0・パイロットの実データを見て調整する。この数値自体に業界標準や先行研究があるわけではなく、コスト(深掘りにかかる工数)と網羅性のトレードオフを運用しながら調整するパラメータとして位置づける。

**手動上書きを許可する理由:** 優先度算定式は機械的な計算だが、顧客側が「この拠点は規模は小さいが評判リスクが高いので深掘りしたい」といった、式に現れない理由で深掘りを希望する場合がある。この経路を残さないと、優先度算定が事実上の「推奨」になり、D-23(システムが推奨しない)の精神に反する。

## 4. 決定事項 D-4:M2固有の除外理由を記録する(M1の除外とは別のフィールド)

M1は「MaterialIssue自体を生成するかどうか」の除外(座標・住所が不明等)を扱う。M2はその先、**「MaterialIssueは生成されたが、深掘り評価には進まなかった」という別の除外判断**を扱う。

```typescript
interface DepthDecision {
  materialIssueId: string;
  depth: "screening" | "deep_dive";
  promotedManually: boolean;
  excludedFromDeepDive: boolean;
  exclusionReason?: string;   // excludedFromDeepDiveがtrueの場合は必須
}
```

**除外理由の記録を必須にする理由(build-plan §5.5より、削らないこと):**
1. ISSA 5000が「重大な項目が見落とされていないこと」の検証を求めており、深掘りされなかった項目についても、なぜ深掘りしなかったかの記録が網羅性の証拠になる
2. M7のG6(選択的開示の検出)を可能にする唯一の情報源になる

**M1の`MaterialIssue.exclusionReason`とM2の`DepthDecision.exclusionReason`は別フィールドとして保持する。** 前者は「評価対象にすら入らなかった理由」、後者は「評価対象には入ったが深掘りしなかった理由」であり、監査時に区別できる必要があるため。
