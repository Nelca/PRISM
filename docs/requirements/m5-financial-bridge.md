# M5:財務接続 — 要件定義

**対象モジュール:** M5(財務接続)
**参照元:** `docs/concept-v2.md` 8.2 / 9.3、`docs/roadmap/build-plan.md` §5.6
**参照:** `docs/requirements/m3-monetization-engine.md`(ValuationRecordの入力元)、`docs/requirements/m6-decision-record.md`(DecisionRecordとの関係・X7の型ガード)
**status:** 確定(D-1〜D-7ですべての論点が決定済み)
**最終更新:** 2026-08-30

---

## 0. 位置づけ

購入理由の一部。**金額を単独で出さず、必ず比較先とセットで出す**(build-plan §5.6)。

**MVP範囲:**
- ブリッジ1:自然調整後利益(交換価値のみ)
- ブリッジ2:社会的費用ビュー(厚生価値のみ)
- 未内部化コスト・内部化率
- 期待損失
- 炭素価格シナリオ3本
- 比較先の提示(営業利益比/減損テストの前提を変えるか/格付・資本コストへの影響)
- ウォーターフォール図
- 非GAAP明示ラベルを全画面・全出力に構造的に付与

**構造制約(実装で崩さないこと、design-rationale-log D-24):**
- 2つのブリッジは物理的に別画面とし、合算を許さない
- 厚生価値ビューは開示専用。投資判断への接続からは分離(除外事項X7、M6のD-1で既に型ガード済み)

**完了条件:** ValuationRecord群から2本のブリッジが生成され、合算が構造的に不可能で、非GAAPラベルが全出力に付く。

## 1. 決定事項 D-1:ブリッジ1(自然調整後利益)の構造

構想書9.3をそのまま型に落とす。

```typescript
interface Bridge1_NatureAdjustedProfit {
  reportedOperatingProfit: number;   // 監査済み報告営業利益。企業提供・PRISMは検証しない(M6 D-4と同じ原則)
  dependencyRiskNormalization: number;   // 依存リスクの正常化調整。交換価値ValuationRecordから算出
  futureInternalizationCost: number;     // 将来内部化見込みコスト。§4の自然債務と接続
  verifiedIncrementalBenefit: number;    // 営業利益へ未反映の、根拠を確認できる増分便益
  natureAdjustedOperatingProfit: number; // = reportedOperatingProfit
                                          //   - dependencyRiskNormalization - futureInternalizationCost
                                          //   + verifiedIncrementalBenefit
  nonGaapLabel: true;                    // 常時付与(§6)
  valueConceptGuard: "exchange";         // 型レベルでexchangeのみ受け付ける(M3・M4・M6と同じbranded typeパターン)
}
```

**理由:** 構想書8.2の規律(価値概念の混在を型で禁止する)を、M5にも一貫して適用する。ブリッジ1の入力は交換価値グループのValuationRecordのみを受け付け、厚生価値タグのレコードを渡すとコンパイルエラーになる設計とする(M3・M4・M6で既に確立したパターンの適用であり、新しい判断ではない)。

## 2. 決定事項 D-2:ブリッジ2(社会的費用ビュー)は物理的に別画面とし、厚生価値のみを受け付ける

```typescript
interface Bridge2_SocialCostView {
  socialCost: number;              // 厚生価値ValuationRecordの中心値
  internalizationRate: number;     // §3参照
  nonGaapLabel: true;
  disclosureOnlyLabel: true;       // 「投資判断には接続されていません」という表示を常時付与(X7の可視化)
  valueConceptGuard: "welfare";    // 型レベルでwelfareのみ受け付ける
}
```

**構造的な合算の禁止:** `Bridge1_NatureAdjustedProfit`と`Bridge2_SocialCostView`は共通の親インターフェースを持たず、両者の値を同じ配列・同じ合計に入れる関数はコンパイルエラーになるようにする(design-rationale-log D-24)。

**X7の可視化:** ブリッジ2の画面には「この数値は開示専用であり、M6の投資判断(DecisionRecord)には接続されていません」という表示を常時付与する。M6のD-1(交換価値のみ受け付ける型ガード)により技術的には既に接続不能だが、利用者が誤解しないよう画面上でも明示する。

## 3. 決定事項 D-3:未内部化コスト・内部化率の定義

```typescript
interface InternalizationStatus {
  totalExternalCost: number;        // 交換価値ValuationRecordの中心値(未内部化コストの総額)
  currentlyInternalizedCost: number; // 既に炭素税・水利用料等の形で実際に支払われている額(企業提供)
  internalizationRate: number;      // = currentlyInternalizedCost / totalExternalCost
  uninternalizedCost: number;       // = totalExternalCost - currentlyInternalizedCost
}
```

**理由:** 「未内部化コスト」はM3が算出する交換価値の総額そのものであり、そこから企業が既に負担している実費(内部化済み分)を差し引いたものと定義する。新しい評価ロジックを追加するのではなく、既存の交換価値ValuationRecordと企業提供の実費データの差分として構成する。

**拠点別集約:** 汚染・廃棄物・土地利用を含む複数カテゴリの交換価値は、カテゴリごとにM5を繰り返さず、1拠点1ポートフォリオとして集約する。各入力は`doubleCountKey`を必須とし、同じキーが複数経路(PRTR移動量と廃棄物入力など)から渡された場合は算定を拒否する。カテゴリ別の総額・内部化済み額・未内部化額・自然債務は内訳として保持する。

## 4. 決定事項 D-4:自然債務は3つの炭素価格シナリオ(NGFS 2種+GX-ETS)を用いて算出する

### 4.1 算出式(構想書9.3)

```
自然債務 = Σ[未内部化コスト × 内部化確率(シナリオ,時期) × 割引係数]
```

**未内部化コストの全額を債務にしない。** 内部化確率という係数を介して見込み額に変換する。

### 4.2 炭素価格シナリオの選定(調査結果に基づく)

独自にシナリオを発明せず、確立されたシナリオセットを採用する。

| シナリオ | 内容 | 出典 |
|---|---|---|
| **NGFS Net Zero 2050(Orderly)** | 積極的な移行が進んだ場合の炭素価格経路 | NGFS Phase V(2024年11月)、NGFS Scenarios Portal |
| **NGFS Current Policies(Hot house world)** | 追加的な対策が取られない場合の炭素価格経路(低位で推移) | NGFS Phase V、同上 |
| **GX-ETS公式価格帯(日本固有)** | 2026年度(義務化初年度)の参考上限取引価格¥4,300/t-CO2・調整基準取引価格¥1,700/t-CO2 | 経済産業省 産業構造審議会 排出量取引制度小委員会(第7回)資料3(2025年12月19日) |

**選定理由:** 日本企業のTCFD/SSBJ開示実務では、グローバルな移行シナリオ(NGFS・IEA)と日本固有の規制価格を組み合わせる方式が一般的である(環境省シナリオ分析実践ガイド等の実例)。NGFSの2シナリオ(楽観・悲観)とGX-ETSの日本固有規制価格を組み合わせることで、「グローバルな移行の不確実性」と「日本の直近の規制現実」の両方を、独自発明なしに表現できる。

**未確認事項(実装前に一次資料で再確認すること):** NGFSの具体的な価格軌道(2030年・2040年・2050年時点の数値)は、二次資料(Carbon Tracker、Green Central Banking等)経由でしか確認できておらず、NGFS Scenarios Portal(ngfs.net)への直接アクセスがブロックされたため、正確な数値は未確認。GX-ETSの2027年度以降の価格上昇見込み(実質3%+インフレ、との言及あり)も一次資料(経産省資料3のPDF本体)での確認が必要。**推定値のまま実装しない**(design-rationale-log D-15)。実装前にこの2点をフェーズ0の追加調査項目とする。

### 4.3 内部化確率の設定方法

**企業(顧客)が各シナリオに主観的な確率を割り当てる。** PRISM側が「このシナリオが正しい」という見解を持たない。

```typescript
interface InternalizationProbability {
  scenario: "ngfs_net_zero_2050" | "ngfs_current_policies" | "gx_ets_official";
  probability: number;   // 顧客が設定。デフォルトは均等割り(各1/3)
  period: number;        // 対象年
}
```

**デフォルトは均等割り(各シナリオ1/3)とし、これは中立的な初期値であることを明示する。** 特定のシナリオを推奨する見解は持たない(design-rationale-log D-23「システムが推奨しない」と同じ原則)。

### 4.4 割引係数

M6のD-4と同じ原則:企業提供の割引率(WACC・ハードルレート等)を流用する。M5独自の割引率は設けない。M5は特定のDecisionRecordに紐づかない全社的な開示指標であるため、企業レベルで1つの代表的な割引率を入力させる(M6は個別の投資判断ごとに割引率を受け取るのに対し、M5は開示単位で1つ)。

## 5. 決定事項 D-5:比較先の提示。格付・資本コストへの影響は定性的な扱いに留める

```typescript
interface ComparisonTargets {
  operatingProfitRatio: number;        // 期待損失 ÷ 報告営業利益
  impairmentTestImpact: {
    changesAssumption: boolean;        // 企業提供の減損テスト前提と比較した結果(§5.3)
    details: string;
  };
  ratingCostOfCapitalImpact: {
    qualitativeNote: string;           // 定性的な記述のみ。定量モデルは持たない(§5.1参照)
  };
}
```

### 5.1 格付・資本コストへの影響を定量化しない理由

構想書11.2は「日本市場における資本コスト効果」を「先行市場の実証はあるが日本・SSBJ固有の効果は未実証」な長期未検証事項として明記している。**この状態で独自の定量モデル(例:自然債務の増加が格付をN段階下げる、資本コストをMbp上げる)を作ることは、根拠のない推定にあたる**(design-rationale-log D-15「推定で埋めない」)。

MVPでは、レバレッジ比率・インタレストカバレッジ比率等、信用アナリストが一般的に参照する指標への影響を定性的に記述するに留め、格付・資本コストへの数値的な影響予測は行わない。

### 5.2 「定性的記述」の具体的な内容(2026-08-02追記)

**表示例:**

```
【比較先:格付・資本コストへの参考情報】

自然債務を加味すると、以下の指標が変化します:

  Net Debt / EBITDA(レバレッジ比率)    2.1倍 → 2.4倍(+0.3倍)
  インタレストカバレッジ比率            8.2倍 → 7.5倍(−0.7倍)

※これらは信用格付機関が一般的に参照する財務指標です。本システムは、
  これらの変化が実際の格付・資本コストにどう影響するかを予測・断定
  するものではありません。[非GAAP指標]
```

**構成要素:**
- 比率の数値(変化前後)は、企業提供の財務データとD-4の自然債務算出結果から**単純な算術で計算する**。解釈の余地はない
- 「格付機関が参照する指標です」「予測・断定しません」という注記文は、**全顧客・全ケースで共通の固定テンプレート文言**である

**この文章生成にAIは使わない。** 数値は算術で計算し、注記文は固定テンプレートとする。理由:M7のD-1(AIには抽出のみ行わせ、判定・評価はルールで行う。「素朴なLLM実装が実態評価を経ずに不適切な回答を生成した事例がある」)と同じ原則をここにも適用する。ケースによって表現が変わったり、うっかり踏み込んだ評価(「格付が下がる可能性が高い」等)をAIが生成するリスクを避けるため、テンプレート+機械的な数値埋め込みという構成に固定する。

---

### 5.3 減損テスト前提との比較は正の損失エクスポージャーだけで行う(2026-08-30改定)

`changesAssumption`は、`lossExposure = Math.max(totalDebt, 0)`としたうえで、`lossExposure > threshold`を比較する。負値を`Math.abs`で正の損失へ読み替えない。

企業負担費用と便益を同じ符号付きフィールドで表すと、便益の絶対値が減損リスクとして発火するためである。費用は自然債務へ、根拠を確認できる増分便益は`verifiedIncrementalBenefit`へ分離し、便益は自然債務・減損閾値・レバレッジ比率と相殺しない。ブリッジ1では営業利益への加算として別段表示する。

また§5.2の表示例にあった比率差分の単位「pt」は「倍」に統一した。ptは%表示の指標のための単位であり、倍率の差分には使わない(同日追記)。

### 5.4 非炭素カテゴリの内部化シナリオと監査証跡(2026-08-30追記)

汚染・廃棄物・土地利用の交換価値には、それぞれ企業入力の`pollution_regulation_and_remediation`、`waste_epr_and_treatment`、`land_restoration_and_offset`シナリオを使用する。総費用、既計上額、確認済み増分便益、確率、時期、金額基準、出典ハッシュ、データ版、二重計上防止キーを入力スナップショットと仮定台帳へ記録する。正規化済み入力全体のハッシュを再計算ハッシュへ含め、値の変更時に保存済み算定結果を再利用しない。

## 6. 決定事項 D-6:非GAAPラベルは全出力に構造的に付与する

```typescript
interface NonGaapLabel {
  label: "非GAAP指標";
  appliesTo: string[];  // 適用対象のフィールド名
}
```

M5が生成するすべての画面・出力(ブリッジ1・ブリッジ2・比較先・ウォーターフォール図)に、型レベルで`nonGaapLabel: true`を必須フィールドとして持たせる。Optionalにしない(design-rationale-log D-15「Optionalにしてよいのは、まだ確認していない外部データだけ」の原則により、表示すべきラベルを省略可能にしない)。

### 6.1 ユーザーから見た具体的な意味(2026-08-02追記)

**ユーザーの入力への影響:なし。** このラベルはユーザーが入力・設定する項目ではなく、システムが自動的に付与する。

**ユーザーの画面表示への影響:** M5が出す数値には常に固定バッジが付随する。

```
┌─────────────────────────────────┐
│ 自然調整後営業利益          [非GAAP指標] │
│ ¥8.2億円                              │
└─────────────────────────────────┘
```

PDF出力・API応答でも同様に、数値データと共に「非GAAP指標である」という情報が必ず付随する。

**「型レベルで必須」の意味は開発者向けの保証である。** `nonGaapLabel`を必須フィールド(オプショナルではない)として定義することで、開発の途中で誰かがラベルなしのデータ構造を作ろうとしても、その時点でコンパイルエラーになり実行前に検出される。ユーザー体験としては単純に「すべての数字に常にバッジが付いている」という状態だが、それが実装のミスで将来消えないようにする、という開発側の保証がこの決定の意味。

## 7. 決定事項 D-7:集中リスクはMVPスコープ外とする(データ構造は既に対応済み)

同一水源に依存する拠点群の相関を考慮した集中リスク分析は、build-plan §5.6が明示的に「後回しでよい」としている。M1のSite全件登録(`docs/requirements/m1-target-definition.md` §1)により、拠点間の関係を後から分析するためのデータは既に蓄積される設計になっているため、M5のMVPでは追加の設計判断を要しない。

---

## 8. 完了条件の確認

D-1〜D-6により、build-plan §5.6の完了条件(2本のブリッジが生成され、合算が構造的に不可能で、非GAAPラベルが全出力に付く)を満たす設計になっている。D-7(集中リスク)はMVPスコープ外のため、この完了条件には寄与しない。

## 9. 備考:確認事項が生じなかった理由

M5の各論点は、M3・M4・M6で既に確立した型設計パターン(価値概念のbranded type分離)と、既存の外部標準(NGFS・GX-ETS、環境省のシナリオ分析実務)の組み合わせで解消できた。格付・資本コストへの影響を定量化しないという判断も、構想書11.2が既にこれを長期未検証事項と位置づけていることから導かれる、恣意的ではない選択である。M1(ENCOREライセンス)・M6(承認閾値入力方式)のような外部事業判断は生じていない。
