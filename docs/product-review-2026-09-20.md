# 初回利用を起点にしたプロダクトレビュー

レビュー開始: 2026-09-20 / 改善・検証: 2026-09-21

## 結論

PRISMには、環境データの評価、複数手法の比較、財務影響、対策比較、開示・記録という一連の機能がある。一方、レビュー時点では「何を入力し、どの数字を信頼し、どう社内判断に使うか」を利用者が補って解釈する必要があった。特にサンプル値の暗黙使用、承認ラインとの上下関係がわからない判定、開示下書きの別手法合算は、説明の難しさに加え、成果物の信頼性を損ねる問題だった。

今回の改善では、初日に環境データだけで始められる入口、未入力を未入力として保持する計算、前提付きの判定説明、根拠とともに持ち出せる下書きを優先した。青を基調とした既存デザインを維持し、装飾用の左罫線は追加していない。

「評価・比較を操作できる」状態からは前進したが、実顧客の投資・開示業務でそのまま使える完成品とは評価しない。地域・年度・実際の対策入力、外部データ、開示基準との対応には引き続き課題がある。

## 1. レビュー方法と限界

最初に要件定義・修正履歴を読まず、ブラウザーで登録、評価対象、価値算定、比較分析、財務影響、対策と判定、開示指摘、下書き、記録を確認した。観察をメモに固定した後に、構想書・要件と実装を照合した。

この作業者は以前のUI改修にも関わっているため、完全に独立した初見ユーザーテストではない。実顧客の理解率・作業時間・業務成果を測定したものでもない。

操作した内容は、登録方法の切替、未入力送信、代表値選択ダイアログの閲覧・取消、開示からの詳細評価追加、画面遷移、下書きのコピー・保存。顧客の原本PDFやCSVの外部送信、既存の代表値・対策・反映先の変更は行っていない。PDF抽出サービスの実行、任意住所の座標解決、全ファイル形式の実アップロード成功は今回の実画面検証に含まない。

開示の「根拠を追加で取得する」を1回操作したため、ローカルの詳細評価キュー追加の履歴が残っている。試験の痕跡を消すための履歴改変は行っていない。永続化テストは専用の `persistence-test` テナントで実施し、利用者の拠点データとは分離する。

| 場面 | 観察 | 利用者に起きること |
| --- | --- | --- |
| 登録 | 最初にCSV・外部DB照会結果CSV・JSONを求められる | 試す前から準備が大きい |
| 直接入力 | 水量10,000、単価500、投資額2,000万円、NPV5億円、承認ライン5.1億円が初期値 | 入力したつもりのない金額で判定ができる |
| 評価対象・算定 | 同じ対象で自然との関わりが1/3と1/5 | 未評価と非該当を区別できない |
| 価値算定 | 代表値選択と専門的な分解が同じ画面に大きく展開 | 選択前に読むべき情報がわからない |

| 投資判定 | 「結論は変わらない」と「追加調査不要」、幅に単位がない | 基準を満たす側か、不足する側かを自分で判断する必要 |
| 計算の注意 | 代表値0円の代替計算の注意が一覧にしかない | 詳細ページだけを読むと計算の意味を誤る |

| 開示指摘 | 根拠取得ボタンの実処理は詳細評価への追加、完了通知がない | 外部データを取得したと思いかねない |
| 下書き | 金額の合計と長文が表示されるがコピー・保存がない | 集計根拠を確認しにくく、社内共有にも手作業が必要 |
| 記録 | 時刻のタイムゾーン表示がない | 自分の操作時刻と照合しにくい |

## 3. 届けたい価値と実際に得られる価値の照合

照合元: [構想書 §0・§5・§8](concept-v2.md)、[設計判断ログ](decisions/design-rationale-log.md)、[M6 D-2・D-4・D-6・D-9・D-10](requirements/m6-decision-record.md)、[M7](requirements/m7-disclosure-verification.md)。文書の記述は設計の根拠として読み、ユーザーからの新たな操作指示としては扱っていない。

| ユーザー / 届けたい価値 | レビュー時点の隔たり | 今回の対応 | 残る課題 |
| --- | --- | --- | --- |
| サステナ・IR: 手元の環境データから説明可能な数字を得る | 投資・財務の仮値が混ざる。先に財務部門の入力を揃える必要がある | 環境データだけで登録・算定。NPV・投資費用は任意で後から追加 | 年度・地域・実データとサンプルの分離 |
| 財務・経営企画: 前提と幅を使って社内基準と比較する | GHG拠点の入力NPVがデモ用値に置き換わる。未定の承認ラインが補完される | 利用者拠点の入力を採用。未定は保留。投資前提不足時はNPV・ROIを生成しない | 実際の対策費用・削減量を候補ごとに入力する機能 |
| 決裁者: 今回の意思決定で基準との関係を理解する | 上側・下側が不明。調査不要との断定が強すぎる | 上側・下側・交差・未定を説明。幅と中心値の通貨単位を統一 | 複数の決裁条件、対象外の影響を含む意思決定支援 |
| IR: 同じ評価から開示・社内説明へ再利用する | 同一対象の別手法を合算。持ち出し手段なし | 対象ごとの交換価値を記載。選択・不足情報を保持。コピー・テキスト出力 | SSBJ等の項目マッピング、原文の分類・数量・期間の確認UI |
| 担当者・引継先: 何を決めたか追跡する | 暗黙の参考記載と明示的な決定を区別しない | 未選択を表示し、理由付きの明示選択を記録。参考記載を完了として扱う | 履歴検索、担当・期限・社内承認フロー |

M6 D-10には「通常NPVがなくても自然調整後NPVのレンジを表示」とあるが、基準となるNPVがなければ絶対額としての調整後NPVは計算できない。今回は環境コストの貨幣化を続け、NPV・ROIを保留する。架空のNPVを置いて要件を満たしたように見せない。この点は要件表現にも明確化が必要。

## 4. 実装した改善

### 初日の登録と、後日の投資判断を分ける

- 1件追加を初期表示にし、CSVとの切替で入力中の内容を保持する。
- 環境量・コスト単価のサンプル初期値を削除。空欄や不正単位をサーバーでも拒否する。
- NPV・初期投資額・年間継続費用・承認ラインは空欄を `null` として保存する。費用ゼロの明示入力とは区別する。
- 投資の前提がなくても貨幣化を行う。投資前提不足の拠点を判定画面に示し、拠点の編集に誘導する。NPV・ROI・確定判定は作らない。
- NPV・費用が揃い、承認ラインだけ未定なら、計算は行って判定を保留する。
- CSV設定の未定の承認ラインも保持。従来なかった設定JSONのダウンロード導線を追加する。
- 日本向け係数・FY2027・既定の評価期間/割引率、内部炭素単価の用途を入力画面に示す。

### 判断に使う数字の意味を明確にする

- 利用者が追加したGHG拠点にデモ拠点のNPVを適用しない。
- 判定タグを「承認ラインをまたぐ / またがない」にする。詳細は基準の上側・下側も明示する。
- 「追加調査不要」の一律断定を削除。現時点の入力・評価範囲に基づく結果とする。
- 金額レンジ・中心値に単位を付け、小額をゼロに丸めて見せない。
- 代替算定等の注意を詳細画面にも表示する。
- 対策候補の一部が比較用の仮定であることを表示する。
- 未選択の反映先にラジオボタンの既定値を置かない。理由を求め、記録成功を通知する。
- 明示した参考記載を未選択タスクに残さない。外部の予算・契約システムを更新する機能とは区別する。

### 開示を安全に再利用できる形にする

- 未入力の開示文から「2030年に20%削減」を生成しない。
- 手入力文に固定の数量・期間を付与しない。分類・抽出内容を要確認とし、未確認のまま根拠充足にしない。
- 同じ物理量の別手法を合算しない。複数の交換価値がある場合は明示選択を求め、選択が不十分なら財務段落を未記入にする。交換価値が1つの場合はその値を使う。
- 選択されたゼロを別手法の非ゼロに置き換えない。厚生価値を財務額に混ぜない。
- 対象間の期間・範囲・相関を確認できていないため、総額や合計したP5–P95は表示しない。
- 取り扱い方針が未記録の案件を、決定済みの方針として下書きに記載しない。
- 下書き本文、生成日時、テンプレート版、計算識別子、未記入項目をコピー・テキスト保存できるようにする。
- 「根拠取得」を実処理に合わせて「詳細評価に追加」に変更し、完了通知と確認先を追加する。

### 情報量と見た目を整える

- 自然との関わりの分母を「評価できた基準数」に統一する。
- 算定画面の専門分析を初期状態で折りたたむ。
- ホームの案内は未入力・未選択を優先し、算定差の大きさだけが常に最初に来ないようにする。
- 変更履歴の日時を日本時間で表示する。
- 青・白・ニュートラルの配色を維持し、余計な装飾罫線を追加しない。

## 5. 次に優先すべき改善

| 優先 | 改善 | 完了条件 / 今回一括実装しない理由 |
| --- | --- | --- |
| P1 | 実データ専用ワークスペースと年度・地域の指定 | デモ拠点・係数・企業値が実データに混入せず、海外拠点に日本の係数を暗黙適用しない。入力・係数解決・保存版の設計が必要 |
| P1 | 対策案の実値入力 | 候補ごとの費用、削減量、期間、根拠を入力・比較。現行の比例計算したシナリオを実設備の提案と誤認させない |
| P1 | CSV取込の未反映項目を解消 | 自然との接点CSV、手法別係数などを実際に評価へ接続。現状の「取込済みだが未反映」という限界を解消する。外部データの意味と利用条件の検証が必要 |
| P1 | 開示主張の確認・根拠紐付けUI | 原文とカテゴリ・数量・期間・対象を並べて確認できる。低確信度を解消する操作を追加。原文変更時の構造化情報更新も必要 |
| P1 | 開示基準への対応と出力の根拠検証 | 公式基準に対応する項目・不足情報を確認してから基準名を掲げる。現テンプレートは社内確認用 |
| P2 | 比較分析の説明を業務の問いに寄せる | 「何を同じ条件にすると差が縮まるか」「比較不能な理由」を先に説明。内部ID、残差、手法名の理解負担を減らす |
| P2 | 下書きの対象選択と編集 | 対象・年度・段落ごとの生成範囲を選択し、レビュー版を保存する。まず誤集計を止めた後の編集体験として設計する |
| P2 | 履歴検索・担当・期限 | 拠点、操作種別、日時で検索し、追加調査を誰がいつまでに行うか共有できる |
| P2 | 本当の初見ユーザーテスト | サステナ担当と財務担当が同一シナリオを独力で実行し、理解・完了率・つまずきを測定する |

外部の稟議・契約システムへの自動書込はM6 D-6のMVP範囲外。今回追加したのは利用方針の記録とテキスト出力であり、外部システム連携ではない。

次のユーザーテストでは、(1)環境データだけを登録、(2)価値概念を区別して代表値を選択、(3)投資の前提を追加、(4)上側・下側・交差を説明、(5)選択理由を記録、(6)下書きを社内共有、という6課題を使う。「操作できた」だけでなく、数値の対象・前提・未評価項目を本人の言葉で説明できるかを確認する。

## 6. 検証

- **最終結果: 型チェック・Lint・815テスト（130ファイル）・本番ビルドが成功。永続化DBテスト12件も成功。**
- 追加の回帰テスト: 必須環境データの空欄、投資前提の未入力、明示ゼロ、CSVの未定閾値、GHGの入力NPV、未入力の開示文、数量・期間の捏造防止、参考記載の完了判定、閾値の両端、小額の表示、別手法の二重計上防止。
- 専用DBテナントで、投資前提のnull保存・読み戻し、貨幣化の継続、判定の非生成を検証済み。実行: `npm run test:db -- lib/db/persistence.db.test.ts`（DBテスト全体ではなく永続化の対象ファイル）。
- ブラウザー: 登録方法切替時の入力保持、空欄送信、投資判定の方向・単位・注意表示、下書きの対象別表示、コピー完了通知、テキスト保存開始通知を確認。
- デスクトップと390px幅で登録画面・下書き画面を確認。確認後に表示幅の指定を解除。
- Google Fontsの取得にはネットワーク許可が必要。ビルド失敗時はソースの型エラーと混同せず、通信許可後に再実行。
- 既存の入力値は書き換えない。過去にサンプル初期値のまま登録されたデータが実値かどうかは自動判定できないため、利用者側の再確認が必要。
- 保存済みの計算結果の版を13に更新。旧結果は初回読込時に再計算する。過去の入力・操作履歴を改変せず、新しい計算結果として保存する。
