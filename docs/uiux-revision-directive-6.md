# PRISM UI/UX修正指示書 第6版(件数スケール設計の全画面適用)

**作成日:** 2026-08-17
**位置づけ:** 第4版・第5版の後続。ユーザーによる3回目のレビューで「/valuationの課題選択が件数増に耐えられない」「/disclosureの指摘が多い場合のUI/UXが悪い」との指摘を受けた。**いずれも第4版で示された原則(「N件(100件規模)になっても成立するUIだけを残す」)の適用漏れ**であり、本版ではまず漏れた理由を構造的に分析し、同種の見落としが残っていないか全画面を棚卸しした上で修正する。
**制約(継続):** `packages/core` 不変。git commitしない。テスト(441+39件)を壊さない。

---

## §0 なぜ同じ指摘が繰り返されたか(原因分析)

### 原因1:「閾値で表示を切り替える」設計は、原則の実装として不十分だった

第4版D-06は「少数(〜8件程度)は現状のピル、それ以上は検索ボックス付きのセレクタ」と指示し、その通りに実装した(`ScalableSelector`、8件以下はピル・9件以上は検索リスト)。しかし**デモデータの課題は3件**なので、ユーザーが見る画面は修正前と同じピルのままだった。ユーザーの目には「何も変わっていない」し、実際、閾値を跨ぐ瞬間にUIの形が変わる設計は(a)ユーザーが検証できない、(b)習熟が引き継がれない(8件のときの操作が9件で通用しない)、(c)閾値付近で行き来すると画面が安定しない、という点で設計として劣る。

**教訓(以後の設計原則):スケールに耐える表現をその画面の唯一の表現にする。件数によって形が変わるUIを作らない。**「少数なら別のもっと良い形がある」と感じるときは、その「良い形」が単なる慣れでないかを疑う。

### 原因2:原則を「指示に列挙された画面」にしか適用しなかった

第4版D-11は「サマリー先行・詳細は要求時」への再設計を④(/financial-bridge)・⑤(/decision)に対して指示し、その2画面だけを修正した。しかし同じ構造問題(「1件ずつの詳細カードを全部縦に並べる」)は⑥(/disclosure)のギャップ指摘一覧にもそのまま存在していた。指示書が画面を名指しで列挙していたため、実装者(前セッションの自分)は**原則の適用範囲を列挙された画面に限定してしまった。**

**教訓:指示書に原則が書かれたら、名指しされた画面だけでなく全画面を同じ原則で監査する。指示の列挙は「最低限ここは直せ」であり「ここだけ直せ」ではない。**

### §0.1 全画面の棚卸し(件数スケール監査、2026-08-17実施)

上記2つの教訓に基づき、「その画面の主要素はN=100で成立するか」を全画面で確認した:

| 画面 | 主要素 | N=100での成立性 | 判定 |
|---|---|---|---|
| / (ホーム) | 進捗6ステップ・タスク一覧・発見サマリー | タスク/発見は種類単位で件数を集約済み(「◯件の課題で…」) | 問題なし |
| /sites | 拠点テーブル+除外行テーブル | テーブルは行が増えるだけ | 問題なし |
| /assessment | 評価対象テーブル(優先度順ソート済み) | テーブル+ソート済みなので上位から読める | 問題なし |

## §A 修正指示

### 指示 D-21 【P0】課題セレクタを「常にコンボボックス」にする(閾値切替の廃止)

- **現象:** /valuationの課題切替が上部のピルボタン横並びのままで、件数が多くなると破綻する(第4版D-06の実装が閾値切替だったため、デモの3件ではピルのまま)。
- **修正:** `app/components/scalable-selector.tsx` を書き換え、**件数に関わらず常に同じ形**にする:
  - 閉じた状態:「選択中の課題名 ▾(全◯件)」を示すトリガーボタン1つ。未対応(代表値未選択)の課題が他にあれば、トリガー上に要対応ドット+件数を出す(C-05のドットの意匠を維持)。
  - 開いた状態:検索ボックス(拠点名・カテゴリの部分一致)+スクロールする選択リスト。各行は従来どおり`<Link>`(URLクエリで対象を切り替える既存方式のまま。サーバー描画とズレない)。要対応ドットは行にも出す。
  - 3件でも100件でも同じ操作。外側クリック・Escで閉じる。選択行には `aria-current`。外部ライブラリ禁止・既存トークンで実装。
  - 旧実装のピルモード・検索リストモード(`.selector-box`)は削除する(参照が無いことをgrepで確認して消す)。比較ペアのピル(`.selector-pills`)は上表のとおり件数がスケールしないため残す。
- **対象:** `app/components/scalable-selector.tsx`、`app/globals.css`、`app/valuation/page.tsx`(呼び出しはprops互換なら変更最小)

### 指示 D-22 【P0】/disclosure をサマリー先行に再設計する(第4版D-11の原則の適用漏れ)

- **現象:** ギャップ指摘が1件=1フルカード(根拠件数・未評価対象テーブル・対応ボタン3種入り)で縦積みされており、指摘が多い場合に全体を見渡せない。
- **修正(④⑤と同じ型):**
  1. **指摘サマリーテーブル**(`id="gap-findings"`、頭出しバナーのアンカー先を維持):1指摘=1行。列は「記載(先頭を切り詰め、全文はtitle)/種別(根拠充足◯ or ギャップ種別タグ+AI抽出確信度低)/一致した根拠件数/対応状況(未対応・理由記録済み・不要)/詳細→」。行の「詳細」リンクは `?finding=<id>#finding-detail`。
  2. **詳細は選択した1件だけ描画**(`id="finding-detail"`)。中身は既存のフルカード(根拠件数・未評価対象・対応アクション3種)をそのまま再利用。既定で開くのは「未対応のギャップがある最初の指摘」、なければ先頭。
  3. 対応状況の判定は `deriveOpenTasks`/`countProgress` と同じソース(`gapType === null` → 不要、`intentionalDecisionRecords.some(r => r.gapFindingId === finding.id)` → 理由記録済み、それ以外 → 未対応)。二重実装しない。
- **対象:** `app/disclosure/page.tsx`

### 指示 D-23 【P1】④⑤の拠点別詳細を「選択中の1拠点だけ」描画する

- **現象:** 第4版D-11でサマリーテーブル化はしたが、拠点別詳細は**全拠点分**を`<details>`(既定は閉)でDOMに描画している。100拠点ではウォーターフォールSVG・比較テーブル×100がHTMLに載り、畳んであっても転送量・描画コストが破綻する。
- **修正:** `?site=`で選択された拠点(既定は最重要拠点)の詳細**だけ**を描画する。他の拠点はサマリーテーブルの行リンクから開く(リンクは既に`?site=...#site-...`形式なのでそのまま機能する)。詳細ブロックに「他の拠点の詳細は上の拠点サマリーの行から開けます」の一文を添える。
- **⑤の付随修正:** 「前提が変わった判定(その他)」の安全弁は、従来「画面に表示されなかったアラート」を拾っていたが、詳細が1拠点だけになると他拠点のアラートが全部ここに落ちて生IDが並ぶ。判定を「**どの拠点の行にも対応しないアラート**(真のはぐれ)」に変え、拠点に紐づくアラートはサマリーテーブルの残タスク列(「判定の見直し」)で伝える。
- **対象:** `app/financial-bridge/page.tsx`、`app/decision/page.tsx`

### 指示 D-24 【P2】「まだ代表値を選んでいない課題」リンクの件数上限

- 選択カード直下の未選択課題リンク(C-05)は課題数に比例して伸びる。先頭5件+「ほか◯件の課題で代表値が未選択です(上の課題セレクタで確認できます)」に上限する。
- **対象:** `app/valuation/page.tsx`

D-21 → D-22 → D-23 → D-24(独立性が高いが、共通CSSはD-21が先)。

- 完了条件: `npm run typecheck` / `npm run lint` / `npm test`(441件)/ `npm run test:db`(39件)全通過。別ポートでのGETスモークテストで全8画面200。
