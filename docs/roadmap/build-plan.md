## 1. 完成の定義

MVP完成とは、以下が一続きで動く状態を指す。

```
拠点データ投入
  → 対象特定(M1)
  → 評価実行(M2)
  → 複数手法で貨幣化(M3)
  → 手法間の乖離を原因分解(M4)
  → 財務指標に接続(M5)
  → 対策を比較し、稟議の閾値をまたぐか判定(M6)
  → 同じレコードから開示文を生成し、根拠充足度を検証(M7)
  → 全判断が前提台帳に記録され、再計算できる(M8)
```

**完成の判定基準は「全機能が動くこと」ではなく「1社分の実データで上記が最後まで通ること」。** デザインパートナー1社のデータで通れば完成、通らなければ未完成とする。

**目標時期:** 2027年1月(フェーズ0の [GATE] をすべて通過した場合)

## 2. 全体工程

```
[P0] フェーズ0 検証            2026年8月〜9月   §3
      ↓ [GATE] C-3a/b/c、C-1、ライセンス
[P1] データモデル確定          2026年9月       §4
      ↓ [GATE] 後から変えられないものが固まったか
[P2] モジュール実装            2026年9月〜12月  §5
      M3 → M4 → M6 → M1 → M2 → M5 → M7 → M8
      ↓
[P3] 統合・横断機能            2026年12月      §6
      ↓
[P4] 実データ通し・パイロット   2027年1月       §7
```

**実装順序が M1→M2→M3… ではない理由(2026-08-02改訂):** 当初(2026-07-31版)は「M1 → M3 → M4 → M6 → M2 → M5 → M7 → M8」としていた。理由は「M4(乖離分解)の型定義が M1 と M3 に波及し、番号順に作ると M4 到達時点で M1・M3 を作り直すことになる」というものだったが、**[GATE]データモデルレビュー(ADR-0003、2026-08-02)を通過し、M1〜M8の型定義はすべて確定済み。型の作り直しを避けるためにM1を先に置くという前提は解消された。**

実際の依存関係を要件定義完了後に再確認したところ、**M1はM3・M4・M6のいずれからも必要とされておらず、必要とされるのはM2からのみ**であることが判明した(M2の物理量アセスメントには感応度スコアが必要なため)。この事実は、M1・M3・M4・M6の要件定義を実際に「M3→M4→M6→M1→M2→M5→M7→M8」の順で進めて何の支障もなかったことでも実証済みである。**購入理由の中心(M3・M4・M6)を最優先で実装し、M1はM2の直前に移す。**

## 5. [P2] モジュール実装

各モジュールは **要件定義 → 実装 → 完了判定** の3段階。要件定義はチャットで詰め、`docs/requirements/mN-*.md` に落としてから実装に入る。

### 5.1 M1: 対象定義と Locate

**位置づけ:** 薄く実装。既存プレイヤー(Natcap、シンク・ネイチャー等)と機能が重複するため、自前構築を最小化する。

**MVP範囲:**
- 拠点・サプライヤーの取込(CSV/スプレッドシート)
- 空間突合(Locate):拠点座標 × 保護区・生態系レイヤ
- 感応度スコアの算出

**要件定義で決めること [HUMAN]:**
- Site / NatureInterface / MaterialIssue の粒度と関係
- 感応度スコアの算出式(どのレイヤをどう重み付けるか)
- WDPA・ENCORE のライセンス条件に応じた実装方式(埋込 / 参照のみ / 利用者ライセンス持込)
- 座標がない拠点の扱い(住所からのジオコーディングか、除外か)

**薄くしてよい:** UI、レイヤ数、ジオコーディング精度
**薄くしてはいけない:** MaterialIssue が課金・監査・開示の共通単位である構造

**完了条件:** 拠点CSVを投入すると MaterialIssue 群が生成され、各々に感応度スコアが付く

### 5.2 M3: 貨幣化エンジン

**位置づけ:** 購入理由の一部。係数自体は既存資産(IFVI等)を使い、**自前構築するのは複数手法の切替・横断比較の基盤**。

**MVP範囲:**
- 1カテゴリ(水)× 2〜3手法(IFVI / 代替費用法 / LIME3)
- モンテカルロによるレンジ算出
- トルネード図
- 適合度ティア(A/B/C)と5次元スコア
- 地理較正(構想書8.4:PPP × 所得弾力性^η × デフレータ × 相対価格 × 面積スケーリング)
- ValuationRecord の生成

**要件定義で決めること [HUMAN]:**
- 手法プラグインのインターフェース(係数セットを差し替え可能にする構造)
- 3層不確実性の扱い(層i パラメータ / 層ii 移転誤差 / 層iii スコープ。**層iii は分布に溶かさず別枠**)
- 適合度ティアの閾値
- ESVD 要約値の使用範囲(**スクリーニング=ティアCのみ。深掘りでは個別レコード照合**。提供元の利用条件と一致させる)
- モンテカルロの反復数(薄くしてよい項目)

**M4 との接続で必須:** ValuationRecord に MethodMetadata(価値概念 / エンドポイント被覆 / 割引率 / 地理較正 / 再計算可能性フラグ)を必ず持たせる。**ここが欠けると M4 が動かない。**

**完了条件:** 同一の物理量に対し複数手法の ValuationRecord が生成され、各々にレンジ・ティア・メタデータが付く

### 5.3 M4: 乖離分解

**位置づけ:** 購入理由の中心。要件定義は完了済み。

**参照:** `docs/requirements/m4-divergence-decomposition.md`

**MVP範囲:** 3要因(エンドポイント被覆 / 割引率 / 地理較正)の対数空間Shapley分解、価値概念による2段構え、フォールバック F-0〜F-9、フットボールチャート

### 5.4 M6: 対策評価と意思決定注入

**位置づけ:** 購入理由の中心。**追加性はここでのみ回収される。**

**MVP範囲:**
- 対応4類型のうち低減・移転(回避・受容は後回し)
- 自然調整後NPV = 通常NPV + Σ 回避される自然関連コスト(割引後)
- 2軸比較(横軸=単位投資あたり財務効果 / 縦軸=単位投資あたり環境アウトカム)
- **★判定(DecisionRecord):レンジが承認閾値をまたぐか**
- **拘束方式の選択と記録**

**要件定義で決めること [HUMAN]:**
- 承認閾値をどう取り込むか(ハードルレート等は経理・経営企画の管轄で、サステナビリティ部門は知らないことが多い。**入力インターフェースの設計が営業難度に直結する**)
- 拘束方式4種の出力フォーマットの違い
  - 弱:稟議書に参考値として記載 → 判定結果だけ渡す
  - 強:稟議の判定式そのものを自然調整後NPVに変える
  - 強:対象拠点の自然関連コストに実際に予算賦課する
  - 強:調達契約の更新条件に組み込む
- 「またがない」と判定したときの出力(5分で終わり、追加課金なし)

**構造制約:** 厚生価値は DecisionRecord に接続しない(除外事項X7)。**交換価値のみで意思決定接続を成立させる。**

**完了条件:** 対策案とValuationRecordを入力すると DecisionRecord が生成され、★判定と拘束方式が記録される

### 5.5 M2: 評価実行(深度可変)

**位置づけ:** 従来通り。M1〜M4 が通ってから実装しても遅くない。

**MVP範囲:**
- 単一パイプラインで深度を引数に取る(スクリーニング / 深掘り)
- 優先度算定
- **除外理由の記録(必須)**

**設計の要点:**
```
優先度 = 感応度 + 財務エクスポージャ + 不確実性の大きさ + 開示必須性
```
**「不確実性の大きさ」を優先度に含めるのが要点。** 深掘りの価値は不確実性の縮小にあるため、投資対効果を事前に見積もれる。

**除外理由の記録を必須にする理由(実装時に削らないこと):**
- ISSA 5000 が「重大な項目が見落とされていないこと」の検証を求めており、網羅性の証拠が必要
- **M7 の G6(選択的開示の検出)を可能にする唯一の情報源**

**MVP範囲のカテゴリ:** 気候・水・汚染の3つ。深度2段階

**完了条件:** 同一パイプラインで深度を切り替えられ、除外した項目とその理由が全件記録される

### 5.6 M5: 財務接続

**位置づけ:** 購入理由の一部。**金額を単独で出さず、必ず比較先とセットで出す。**

**MVP範囲:**
- ブリッジ1:自然調整後利益(**交換価値のみ**)
- ブリッジ2:社会的費用ビュー(**厚生価値のみ**)
- 未内部化コスト・内部化率
- 期待損失
- 炭素価格シナリオ3本
- 比較先の提示(営業利益比 / 減損テストの前提を変えるか / 格付・資本コストへの影響)
- ウォーターフォール図
- **非GAAP明示ラベルを全画面・全出力に構造的に付与**

**構造制約(実装で崩さないこと):**
- **2つのブリッジは物理的に別画面とし、合算を許さない。** 厚生価値を利益から引くと企業の損益に社会的費用が混入して意味をなさない
- 厚生価値ビューは開示専用。投資判断への接続からは分離(除外事項X7)
- 自然債務 = Σ[未内部化コスト × 内部化確率(シナリオ,時期) × 割引係数]。**未内部化コストの全額を債務にしない**

**後回しでよい:** 集中リスク(同一水源に依存する拠点群の相関考慮)。ただしデータ構造は M1 の全拠点登録で既に成立している

**完了条件:** ValuationRecord群から2本のブリッジが生成され、合算が構造的に不可能で、非GAAPラベルが全出力に付く

### 5.7 M7: 開示生成と整合検証

**位置づけ:** 予算科目と締切が存在する唯一の入口。差別化要因ではないが、導入の起点になる。

**MVP範囲:**
- 入力は**既存の統合報告書・TCFD開示**(自社が過去に公表した文書)
- 4段階処理
- **G1〜G4 のみ検出**(G5〜G8 は後回し)
- 推奨アクション3種

**4段階:**
```
段階1: AIで DisclosureClaim を抽出(抽出のみ。真偽判定はさせない)
段階2: 主張タイプの分類(状態/定量/傾向/比較/純量/将来約束)
段階3: 根拠の紐付けと充足度判定
段階4: ギャップ類型の判定
```

**実装上の必須制約 [AI に必ず伝える]:**
> **AIの役割は抽出に限定する。判定はルールで行う。** 素朴なLLM実装は実態評価を経ずにグリーンウォッシュと区別できない回答を生成した事例がある。段階3・段階4 に LLM を使わない。

**ギャップ類型:** G1 根拠不在 / G2 根拠薄弱(ティアCのみ) / G3 範囲不一致 / G4 期間不一致 —— ここまでがMVP。G5 定義不一致 / G6 選択的開示 / G7 相殺依存 / G8 約束の裏付け欠如は後続

**推奨アクション:** ①主張を弱める ②根拠を追加取得する(深掘りへの導線=課金) ③意図的判断として記録する。**③を用意しないと実務で使われなくなる**

**用語の制約:** 「グリーンウォッシュ判定」ではなく「主張の根拠充足度」。断定的評価は法的リスクを伴う。**他社評価は行わない**(除外事項X6)

**MVPで入力を既存公開資料にする理由:** 材料待ちの問題が消え、導入初日に価値が出る

**完了条件:** 自社の過去開示PDFを投入すると DisclosureClaim が抽出され、G1〜G4 のギャップが検出される

### 5.8 M8: 記録・版管理基盤

**位置づけ:** **継続理由であって購入理由ではない。** 構造は初日から完全に、UIは最小に。営業では前面に出さない。

**MVP範囲:**
- AssumptionEntry の蓄積(**判断が発生する全箇所で自動生成**)
- 再計算ハッシュ
- 係数セットの版管理と旧版での再計算
- ライセンス区分の制御(埋込可 / 参照のみ / 要利用者ライセンス)

**実装の要点:**
- AssumptionEntry は「後から手で入力する」設計にしない。M2の除外理由、M3の手法選択、M4のフォールバック適用と一致階層、M6の拘束方式選択が、**発生と同時に自動で台帳に入る**
- 再計算ハッシュの入力には、係数版・手法版・M4の一致階層・AoP対応表の版を含める

**後回しでよい:** DecisionRecord の実績照合(n年後の乖離アラート)。**初年度には価値を生まない。**構造だけ用意し、機能は後で

**完了条件:** M1〜M7 のすべての判断箇所から AssumptionEntry が自動生成され、任意のレコードを旧版係数で再計算できる

## 8. 分岐 — [GATE] が不通過だった場合

**失敗時に慌てて設計を歪めないために、先に書いておく。**

### 8.1 AoP 対応表が作れなかった場合(§3.1 不通過)

1. **対象手法を絞る** … 対応付け可能な2手法に限定。カバレッジは落ちるが購入理由は残る
2. **分解の粒度を落とす** … 「人間影響 / 生態系影響」の2分類まで粗くする。情報量は減るが「何が違うか」は言える
3. **分解を諦め、メタデータ差異の並記に留める** … 構想書9.3 が明示的に否定した「3本並べただけ」への退化。**M4 の購入理由が消える**

**1と2は縮小、3は撤退。混同しないこと。**

### 8.2 再計算が広範に不能だった場合(§3.2 で要注意判定)

出力が「説明済み ×1.1 / 残差 ×2.4」のようになる。この状態で価値があるかを C-1 で直接確認する。

**残差が支配的でも価値がある可能性:** 「この乖離は既知のパラメータでは説明できない」こと自体が監査上・意思決定上の情報になりうる。ただしこれは仮説であり、C-1 で検証されるまで前提にしない。

### 8.3 支払意思が確認できなかった場合(§3.3 不通過)

構想全体の再検討。M4 の技術検証が通っていても実装に進まない。

## 9. AIへの指示の出し方

実装をAIに任せる際の規律。**これを守らないと、動くが監査に耐えないコードが積み上がる。**

### 9.1 指示に必ず含めること

1. **参照すべき要件定義のパス。** 「構想書に従って」ではなく「`docs/requirements/m4-divergence-decomposition.md` の §5 に従って」
2. **薄くしてよい箇所と、してはいけない箇所。** AIは指定しないと全部を等しく作り込むか、等しく手を抜く
3. **推定で埋めてはいけない箇所の明示。** 「データが取れない場合は推定値を入れず、`uncomputable` を返す」
4. **テストを先に書かせる範囲。** M4のフォールバック、M8のハッシュ再現性は特に

### 9.2 指示してはいけないこと

- 「よしなに」「一般的なやり方で」— 本製品は一般的なやり方を意図的に外している箇所が多い
- 仕様の未確定部分を含んだまま実装を投げる — AIは埋めてしまう
- 除外事項(§10)に触れる実装 — 明示的に禁止を伝える

### 9.3 レビューで必ず見ること

| 観点 | 見る箇所 |
|---|---|
| 推定で埋めていないか | `null` / `unknown` を返すべき箇所にデフォルト値が入っていないか |
| 価値概念の混在 | 交換価値と厚生価値が同じ配列・同じ合計に入っていないか |
| 前提の記録漏れ | 判断が発生する箇所で AssumptionEntry が生成されているか |
| ラベルの欠落 | フォールバック適用、非GAAP、ティア、除外事項が出力に付いているか |

## 10. 実装ガード — 作ってはいけないもの

構想書9.4 の除外事項。**AIは指定しないとこれらを「親切に」実装してしまう。**

| # | 禁止 | 理由 |
|---|---|---|
| X1 | 自然の状態(種・生態系状態)の貨幣化 | TNFD自身が単一指標の不在を認めている |
| X2 | 鉱物資源の枯渇の貨幣化 | 手法間5桁の乖離 |
| X3 | 侵略的外来種の貨幣化 | 適用ロジック不在。物理単位のみ |
| X4 | GHGインベントリ算定エンジン | 既存プレイヤーの領域 |
| X5 | 独自の統合スコア | 標準戦争に巻き込まれない |
| X6 | 他社評価 | 法的リスク、スコープ外 |
| X7 | 厚生価値の DecisionRecord への接続 | 厚生価値は開示専用 |

**加えて、実装で起きやすい違反:**

- エンドポイント重複を**自動控除する** … 検出し、選択肢を示し、選択を記録する。自動処理すると根拠不明の調整が数字に埋め込まれる
- 相殺(P4:炭素固定サービス × GHG排出)を既定で有効にする … **既定で禁止**。有効化には根拠・地理的時間的一致・恒久性の説明を必須とし、総量と純量を必ず併記
- 代表値をシステムが推奨する … 提供するのは判断材料であって推奨ではない
- 手法変更時に前年度手法での再計算値を出さない … 手法変更の差分と実態変化の差分が混ざる
