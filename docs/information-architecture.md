# PRISM 情報設計(IA)— 要件の本質抽出と画面への反映

**作成日:** 2026-08-23
**経緯:** デプロイ後のレビューで「何も知らないユーザーには、何をどうすれば良いのか・何ができるようになるのかが分かりづらい」という指摘を受けた。本書は、要件定義(`docs/concept-v2.md`・`docs/requirements/m1〜m8`)から本質的な価値を抽出し直し、それを情報設計(IA)として整理した上で、現状UIへの反映方針を定める。
**制約(継続):** `packages/core` 不変。git commitしない。テストを壊さない。件数スケール設計原則(スケールに耐える表現を唯一の表現にする)を維持する。

## 1. 要件定義から抽出した「本質的にやるべきこと・やりたいこと」

構想書v2を読み直すと、プロダクトの価値は次の1文に集約される。

> **企業が既に持っている環境データを、「この数字は、この決定を変えるか」という判定に変換する。**(concept-v2 §4.2・§8.1)

この1文を支える構造は以下のとおり。UIが伝えるべきなのは工程ではなく、まずこの構造である。

### 1.1 出力は3層 = ユーザーが受け取る「3つの成果物」

| 出力層 | 成果物 | 誰の何に効くか |
|---|---|---|
| DecisionRecord(★判定) | **投資判断への判定**:自然関連コストのレンジが承認基準をまたぐか。「またがない」=この論点はこの決定を変えないと確定(安く・速く・追加調査を打ち切れる)。「またぐ」=結論が変わりうるので、レンジを支配する前提だけを深掘りすればよい | 事業部・決裁ライン(判断可能性)、CFO/経営企画(使用可能性) |
| DisclosureView | **開示の記載と根拠**:判定と同じレコードから開示文の下書きと、既存開示文言の根拠充足の確認結果 | サステナ/IR(説明可能性)。予算科目と締切が存在する唯一の入口(§9.3 M7) |
| AssumptionEntry(M8) | **監査証跡**:誰がいつ何を選び、なぜか。担当が変わっても・監査で聞かれても再現できる | 監査・保証対応。継続理由(購入理由ではない) |

- レンジ(フットボールチャート)は結論ではなく道具。**判定が結論**(§6.1)。
- 「開示用の数字」と「投資判断用の数字」が同じレコードから出ることが、単発コンサルに対する唯一の構造的優位(§6.3)。
- 中核の差別化は「乖離の原因分解」:手法間の差を精度の問題ではなく「問いの違い」として説明できること(§8.6)。

### 1.2 信頼の規律は、それ自体が価値である

構想書・要件定義を貫く規律は、機能ではなく「この数字を社内で使える理由」そのものであり、初見ユーザーに明示する価値がある。

- 推奨値を出さない。代表値・対策・反映先はユーザーが理由付きで選ぶ
- 分からない値を仮置きしない(承認閾値未入力なら判定は「保留」。M6 D-10)
- 除外・失敗は黙って消さず、理由付きで残す
- AIはPDFからの抽出のみ。算定・判定・文章組み立てには使わない
- 厚生価値(社会全体への影響)は開示専用で、投資判断の金額と合算できない(§8.2)

### 1.3 利用の時間軸:年間サイクル(§6.3)

Q1 開示準備(データ投入→算定→開示下書き)→ Q2 開示(前提台帳が保証対応の材料)→ Q3 予算・投資(同じレコードを稟議の判定に接続)→ Q4 中計(対策ROI・拘束方式の見直し)。「一度きりの評価ツール」ではなく「毎年・毎四半期の反復利用」であることが利用イメージの前提。

## 2. 現状UIの診断:なぜ初見ユーザーに伝わらないか

### 2.1 何が問題でないか(維持するもの)

- 一本道6ステップ+参照画面という**ワークフロー層の構造**は、要件(縦串パイプライン)と整合しており正しい
- 各画面のガイド文(「この画面では〜します」+操作手順)・空状態の3点セット・タスク導出の単一ソース化・件数スケール設計は、いずれも機能している
- 各画面内の情報密度・規律表示(非GAAP・保留・除外理由)も要件どおり

### 2.2 問題の所在:オリエンテーション層の欠落

| # | 診断 | 具体 |
|---|---|---|
| 診断1 | **プロダクトの目的をどこも説明していない** | ブランドタグ「自然資本の意思決定レイヤー」以外に、PRISMが何を解決し何を出すのかを述べる場所がない。ホームは「いまどこまで進んでいるか」から始まり、ワークフローに既にコミットした人向けの画面になっている |
| 診断2 | **IAが「処理工程」軸のみで、「成果物」軸がない** | ナビは 評価する→判断する→開示する という処理の順序。初見ユーザーの関心(「使うと何が手に入るのか」)に対応する概念がIA上に存在しない |
| 診断3 | **価値の証拠が⑤⑥まで進まないと見えない** | ★判定(価値の中心)は⑤の画面内、開示下書きは⑥の末尾にある。ホームの「分かったこと」は結果の一部を出すが、「これが成果物だ」という枠組みでは提示されない |
| 診断4 | **各画面の操作は分かるが、操作の理由(下流との接続)が薄い** | 「代表値を選ぶ」ことは分かるが、それが★判定と開示の根拠に使われるから必須なのだ、という因果はガイド文の外にある |

原因は第1〜6版の指示書がすべて「ワークフロー層の中の改善」(操作性・スケール・整合)だったことにある。初見ユーザーが最初に必要とする「利用イメージと価値」を担う層が、そもそも設計されていなかった。

## 3. IA設計

### 3.1 情報の3層モデル(新設は第1層のみ)

```
第1層 オリエンテーション層(新設)
      「PRISMは何を出すのか」— 3つの成果物・入出力の対応・年間サイクル・信頼の規律
      担い手: 「はじめに」画面(/guide)+ ホーム冒頭の成果物ブロック

第2層 ワークフロー層(既存・構造維持)
      ①データと拠点の登録 → ②評価対象の絞り込み → ③価値の算定と代表値の選択
      → ④財務への影響 → ⑤対策と判定 → ⑥開示への反映

第3層 参照層(既存)
      記録(監査証跡)
```

### 3.2 最上位概念は「成果物」:ホームを「価値→現在地→次の行動」の順に

ホームの役割を「現在地と次にやること」から「**このプロダクトが出すもの・現在地・次にやること**」に拡張する。

- 冒頭に「3つの成果物」ブロックを置き、**実データの件数と現在の状態**(判定 確定◯/◯件・開示の根拠確認◯/◯件・監査証跡◯件)を成果物の枠組みで示す。初見ユーザーには価値の説明、常用ユーザーには成果物の現況ダッシュボードとして働く(同一表現・状態で形を変えない)
- 注: 旧指示04で「M6の判定表・M8の件数カードはホームから外す」と決めた経緯があるが、あれは**判定表・課金明細の再掲**の禁止であり、本ブロックは件数+1行の成果物サマリーに留めるため衝突しない
- リード文を工程説明からバリュープロポジション(§1の1文)に差し替え、「はじめに」への導線を置く

### 3.3 「はじめに」画面(/guide)— オリエンテーション層の本体

初見ユーザーが「利用イメージと価値」を1画面で掴めるページ。ワークフロー外の静的な説明画面(記録と同じく参照層に置き、ステップ導線には混ぜない)。構成:

1. **何をするプロダクトか** — §1の1文+「複数手法を並列適用し、差の理由を分解する。1つの正解を推さない」という差別化
2. **得られる3つの成果物** — §1.1の表を初見向けの言葉で
3. **使い方の流れ** — 6ステップ×「入れるもの→得られるもの」の対応表(下記3.4)。工程名ではなく入出力で利用イメージを作る
4. **年間サイクルでの位置づけ** — Q1〜Q4(§1.3)
5. **数字を信頼できるものにするための決まりごと** — §1.2
6. **最初の一歩** — デモデータで一巡する導線+自社データ登録への導線

### 3.4 ワークフロー層の「入れるもの → 得られるもの」対応(IAの中核表)

各ステップを工程名ではなく入出力で定義し直す。この表が「はじめに」の流れ説明の原典であり、各画面のガイド文の第1文とも整合させる。

| 画面 | ユーザーが入れるもの | 得られるもの(下流で何に使われるか) |
|---|---|---|
| ①データと拠点の登録 | 拠点一覧と環境データ(CSV一括 or 1件ずつ) | 拠点ごとの感応度(自然との関わりの強さ)。以後すべての算定の土台 |
| ②評価対象の絞り込み | 詳細評価に進める課題の指定(優先度は自動算定) | 詳細評価の対象一覧(対象外も理由付きで残る) |
| ③価値の算定と代表値の選択 | 投資判断に使う代表値の選択(理由付き) | 複数手法による金額の幅+差の理由の分解。代表値は④⑤⑥の入力になる |
| ④財務への影響 | 自社の財務データ(営業利益等) | 自然調整後利益・期待損失と比較先 |
| ⑤対策と判定 | 通常NPV・承認閾値・対策の選択・反映先 | **★判定:承認基準をまたぐか(成果物1)** |
| ⑥開示への反映 | 開示物のPDF(任意) | **開示文の下書き+根拠整合の確認(成果物2)** |
| 記録 | (操作不要) | **監査証跡(成果物3)** |

### 3.5 ナビゲーション・ラベリング方針

- ナビの3グループ(評価する/判断する/開示する)・6項目のラベルは第1〜6版で安定しており**変更しない**(習熟の破壊を避ける)
- ナビ下部(参照層)に「はじめに(できることと使い方)」を追加する。初見ユーザーの主導線はホーム冒頭のリンクが担い、ナビは再訪用
- 文言の規律: 断定・推奨をしない既存の言い回し(「結論が変わるか」に徹する等)を、新設するオリエンテーション文言にもそのまま適用する

## 5. 追補(2026-08-23 第2回レビュー):ホームの図式化と用語の見直し

レビュー指摘:「全てが文字文字しく、ITリテラシー・読解力が低い場合には分からない。概念的な図・表・グラフで表現する。特にトップページ。文言はできる限り単語のみとし、説明的・長いものは避ける」。

### 5.1 ホームの再設計(IA-06)

- 冒頭の成果物カードを文章タイルから**流れ図**に変更:環境データ → 金額に換算 → 成果物3行(判定・開示・記録)。各ノードはアイコン+単語+件数バッジ、判定・開示は内訳の割合バー付き。件数が増えても形は変わらない(スケール原則)。
- 件数の導出は `deriveOutcomeSummary`(進捗と同一ソース)に集約したまま拡張。
- 左上のPRISMロゴをホームへのリンクにする(IA-07)。

### 5.2 用語の見直し(IA-08):意味と新表記の対訳

方針:画面には**短い日常語**を出し、正確な定義はhover(title)に退避する。判定は「またぐ/またがない」の比喩をやめ、意味そのもの(結論が変わるか)を言い切る。投資可否・記載の真偽を断定しない規律は全表記で維持。

| 旧表記 | 意味 | 新表記(hoverに正確な定義) |
|---|---|---|
| 通常NPV/通常時NPV | 自然コストを含めない、通常の稟議で使う正味現在価値(投資が生む将来利益の現在換算合計) | **投資価値(NPV)** |
| 自然調整後NPV/投資対効果(NPV) | 上記に自然関連コスト・便益を加えた値 | **自然コスト反映後の投資価値** |
| 承認閾値/承認基準 | 社内で投資が承認される基準の金額(投資稟議のハードル) | **投資の承認ライン** |
| 基準をまたぐ | 反映後の投資価値の幅が承認ラインと交差=投資判断の結論が変わりうる | **結論が変わる可能性** |
| 基準をまたがない | 幅が承認ラインと交差しない=この論点はこの決定を変えないと確定 | **結論は変わらない** |
| 開示claim文 | 開示物に書かれた主張の一文 | **開示の記載文** |
| 感応度 | TNFDの5基準のうち該当した数(0〜5)。大きいほど自然への依存・影響が強く、優先度が上がる | **自然との関わり** |
| 移転なし | 他地域の研究値の借用(便益移転)をしていないため、借用誤差の等級A/B/Cの対象外 | **直接算定** |
| 報告営業利益 | 決算書(監査済み財務諸表)に載っている営業利益 | **営業利益(決算値)** |
| 減損テスト前提の閾値 | 資産の帳簿価値を見直す会計手続き(減損テスト)で前提としている金額 | **減損の目安額**(表の列は**減損リスク**) |
| 調整幅(営業利益比) | 自然コストを差し引いたときの営業利益の変化率 | **利益への影響** |
| 自然調整後営業利益 | 営業利益(決算値)−自然関連の将来コスト2種、のPRISM試算値 | **自然コスト反映後の営業利益** |
| 非GAAP指標 | 監査済み決算書の数値ではない、PRISM独自の参考値 | **社内試算値(決算数値ではありません)** |

付随して、ナビ・工程ラベルを短縮した:「データと拠点の登録」→**拠点データの登録**、「価値の算定と代表値の選択」→**価値の算定**。coreが生成するラベル(ウォーターフォールの「報告営業利益」等)は `financialDisplayLabel()`(app/components/labels.ts)で表示時にのみ読み替える(packages/core不変)。

### 5.3 ホームの金額サマリー(IA-09、2026-08-23 第3回レビュー)

「トップページに貨幣価値の判断結果サマリーを出せないか」の要望を受け、流れ図の直下に**「金額でみる評価結果」**カードを追加した。

- 1拠点1行:利益への影響(0を中心に左右へ伸びる比較バー+%)/自然債務(期待損失)/判定タグ/④詳細への導線。末尾に自然債務の合計行
- 導出は `deriveMoneySummary()`(lib/pipeline/open-tasks.ts)に集約し、④の拠点サマリーも同じ関数を参照する(数値の食い違いを作らない)
- 規律:合算するのは交換価値由来の自然債務のみ(厚生価値は混ぜない=X7)。利益への影響は比率のため合算せず、その旨を合計行に明記。カードには「社内試算値」バッジを付す
- スケール:行が増えるだけのテーブル+同一バッチ内の最大絶対値を基準にした割合バーで、件数が増えても形は変わらない
