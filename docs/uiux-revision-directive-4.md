# PRISM UI/UX修正指示書 第4版(機能バグ+ユーザー目線の再設計)

**作成日:** 2026-08-17
**位置づけ:** 第1〜3版の後続。ユーザーによる実操作レビュー(2026-08-17、スクリーンショット2枚)で判明した**機能バグ3件+エラー処理の構造欠陥**と、/valuation・/financial-bridge・/decision のユーザー目線での再設計指示。
**制約(継続):** `packages/core` 不変(※D-14のダミーデータ調整は `lib/demo` であり対象外)。第1版§5「維持すべき点」を壊さない。git commitしない。

## §0 総評

今回の指摘は2群に分かれる。

- **機能バグ(最優先):** 代表値の変更・企業財務データの入力がサーバー例外(`M6 D-3: 深掘り推奨を算出できるValuationRecordがありません…`)で失敗する。さらに深刻なのは、**エラーになる操作イベントが先にDBへ永続化される**ため、以後のあらゆる操作が同じ例外で失敗し続けること(ユーザーの「エラー後にブラウザバックで対象画面が表示されない」もこの系)。
- **設計の欠陥:** (1)「拠点ごとの詳細を全部並べ、やるべきことは最下部」という構成が /financial-bridge・/decision に残っており、スクロール強制かつ課題数の増加に耐えない。(2)独自用語(自然調整後営業利益・未内部化コスト等)と判定文言(またぐ/またがない)が説明なしで使われている。(3)課題セレクタ・ペア比較・グラフが「デモの件数でしか成立しない」実装になっている。

原則(第3版から継続+追加): **サマリー(やるべきこと)が先、詳細は要求時。すべての操作は失敗してもシステムを壊さず、その場でエラーを返す。N件(100件規模)になっても成立するUIだけを残す。**

## §A 機能バグ(P0・最優先)

### 指示 D-01 【P0】代表値変更・財務データ入力の例外と「操作不能の連鎖」を根治する

- **現象:** ③で代表値を変更、④で企業財務データを入力すると「M6 D-3: 深掘り推奨を算出できるValuationRecordがありません(countermeasuresが空か、sourceValuationRecordIdが解決できません)。」で失敗する。
- **調査済みの手がかり:**
  - 例外の発生源は `packages/core/src/decision/dominant-assumption.ts:58`(変更不可)。`countermeasures[].avoidedNatureCost[].sourceValuationRecordId` が `valuationRecordsById` で解決できないと投げる。
  - `lib/demo/run-demo-pipeline.ts` は `buildCountermeasureCandidates(representative.id)` 等で対策を作り、`valuationRecordsById: { [representative.id]: representative }` を渡している。代表値の上書き(interaction)適用後にこの対応が崩れるケースがあるはず。`buildCountermeasureCandidates` / `buildClimateCountermeasureCandidates` / `buildUserCountermeasureCandidates` の実装と、代表値上書きの適用順を追って**根本原因を特定して直す**(修正は `lib/demo`・`lib/pipeline`・`app` の範囲で)。
  - **構造欠陥:** 各Server Action(代表値選択・財務入力・対策選択・反映先・閾値入力・深さ切替等)は「interactionをDBに追記 → `executeAndPersistRun`」の順で実行しており、パイプラインが例外を投げる操作でも**イベントだけが永続化される**。以後は入力が変わるたびに同じ例外になり、全操作が失敗し続ける(ユーザー環境は現にこの状態の可能性が高い)。
- **修正:**
  1. 根本原因(上記)を特定し、正しい代表値変更でパイプラインが通るようにする。
  2. **「検証してから永続化」に全アクションを改める:** 変更後のinteraction状態をメモリ上で合成して `runDemoPipeline` を先に実行し、成功した場合のみイベント追記+run永続化する共通ヘルパー(例: `lib/pipeline/try-run-with-interaction.ts`)を作り、interactionを書く全Server Actionを載せ替える。失敗時はDBに何も書かず、FormStateで平易なエラー文を返す(生の例外メッセージを画面に出さない。「この変更を適用できませんでした。◯◯…」+記録用に元メッセージはconsole/サーバーログへ)。
  3. **既に汚染された状態の回復:** ユーザーのDBに残っている「パイプラインを壊すイベント」があっても、1の根本修正で解釈可能になることを確認する。解釈不能なイベントが残るケースがあるなら、パイプライン実行時に該当interactionを無視して警告表示する防御を `lib/demo/run-demo-pipeline.ts` 側に入れる(黙って無視せず、画面に「適用できなかった操作が1件あります」と出す)。
  4. 再現手順での検証: 代表値を各交換価値手法へ変更→成功すること。④の財務入力→成功すること。失敗ケース(意図的に壊した状態)でフォームエラーが返り、**ページ遷移・再訪・ブラウザバックが正常**なこと。
- **対象:** `lib/demo/run-demo-pipeline.ts`・`lib/demo/company.ts`(candidates構築)・`lib/pipeline/`(新ヘルパー)・`app/**/actions.ts` 全部

### 指示 D-02 【P0】「まだ代表値を選んでいない課題」の誤表示を直す

- **現象:** ③で代表値を選択済みの課題(例: 本社工場 × 取水量・水ストレス)が「まだ選ばれていません →」に出る。
- **原因の見立て:** 判定ソースの不一致。C-05は `DivergenceDecomposition.representativeValueSelection`(ユーザーが明示選択した場合のみ存在)で判定しているが、既定の代表値(`representativeRecordByMaterialIssue`)で運用中の課題との区別、あるいはID照合のズレがある。`deriveOpenTasks` の representative-value タスクと**同一の判定関数**に一本化し、二重実装を解消する。
- **対象:** `app/valuation/page.tsx`、`lib/pipeline/open-tasks.ts`(判定関数の共通化)

### 指示 D-03 【P0】methodIdのサブ係数付き生表示を全廃する

- **現象:** 「ifvi-water-consumption.VFnutrition」「ifvi-water-consumption.VFaccess」等がそのまま表示される(手法表・幅が違う理由のsubtitle・ウォーターフォールのラベル等)。METHOD_LABEL辞書はベースID(`ifvi-water-consumption`)しか持たず、サブ係数付きIDでフォールバックが発動している。
- **修正:** `methodLabel()` をサブ係数対応にする。`packages/core` のIFVI水プラグイン実装と `docs/data/` の対応表を確認し、VF系サブ係数の正しい日本語名(例: VFaccess=水アクセス、VFnutrition=栄養(食料生産)、VFes=生態系サービス等——**実装・原典を確認して正確に**)を辞書化し、「IFVI 水ストレス係数(◯◯)」形式で表示。未知のサブ係数はベース名+サブ係数コードで表示(完全な生IDは出さない)。全画面のフォールバック箇所をgrepで点検。
- **対象:** `app/components/method-labels.ts`(または labels.ts)、参照全画面

### 指示 D-16 【P0】クラッシュ時の回復動線(Error Boundary)

- **現象:** サーバー例外時にNext.jsの素のエラー画面になり、復帰の動線がない。
- **修正:** App Router の `error.tsx`(+必要なら `global-error.tsx`)を追加し、「問題が発生しました/操作は保存されていません/再試行・ホームへ戻る」を既存デザイントークンで表示。`node_modules/next/dist/docs/` のエラーハンドリングガイドに従うこと。D-01の事前検証により通常操作でここに落ちることは無くなる前提の、最後の受け皿。
- **対象:** `app/error.tsx`(新設)ほか

## §C /valuation(P1)

### 指示 D-05 【P1】「算定の対象」カードの重複整理

- 課題セレクタ(拠点×カテゴリ)の直下の「算定の対象」カードが、対象拠点・対象カテゴリを再表示している。重複を削り、カードは「感応度」「物理量(取水量◯m3/年等の実数)」「手法数」のような**セレクタに無い情報だけ**にするか、手法一覧カードのヘッダーに統合して削除する。
- **対象:** `app/valuation/page.tsx`

### 指示 D-06 【P1】課題セレクタの100件スケール対応

- ピルの横並びは100件で破綻する。**件数で表示を切り替える**: 少数(〜8件程度)は現状のピル、それ以上は検索ボックス付きのセレクタ(拠点名・カテゴリで絞り込めるリスト。既存トークンで実装、外部ライブラリ禁止)。未選択ドット(C-05)はどちらのモードでも表示。同じコンポーネントを/financial-bridge・/decisionの拠点切替(D-11)でも使えるよう汎用化する。
- **対象:** `app/components/`(新コンポーネント)、`app/valuation/page.tsx`

### 指示 D-07 【P1】「差が生じる理由」「幅が違う理由」を比較ペア選択式にし、読める図にする

- **現象(スクリーンショット):** (1)ウォーターフォールのX軸ラベルが重なって判読不能。(2)片方の値が0のとき加法フォールバックになり、棒2本だけで「なぜ差が生じるのか」が読めない。(3)「幅が違う理由」が固定ペア(welfare先頭2件)で、ユーザーが見たい代替費用法 vs IFVI(VFes)のペアと食い違う。(4)そもそも「中心値の差の分解」と「幅(P5〜P95)の違いの分解」が別の分析であることが伝わらない。
- **修正:**
  1. **ペア選択UI:** 比較する2手法をユーザーが選べるようにする(同一価値概念グループ内のペアのみ。既定は乖離倍率が最大のペア)。「差が生じる理由」(中心値)と「幅が違う理由」(レンジ幅)は同じ選択ペアに連動させ、両カードのsubtitleに「◯◯ と ◯◯ の比較」を明示。分解データは `divergenceDecompositions` の全 `pairwiseDecompositions` から該当ペアを引く(存在しないペアは選択肢に出さない)。
  2. **ウォーターフォールの可読化:** ラベルの重なりを解消(ラベルを軸下2段に振り分ける/バー上に値・下に短縮名/横向きレイアウトへの変更、いずれか実装しやすく読める形)。要因バーの色分けと、`pair.narrative`(読み下し文)を図の直下に本文として常設表示(現在はtooltip-note扱いで読み飛ばされる)。
  3. **ゼロ値・フォールバック時の説明:** 加法分解フォールバック文はそのまま出すのではなく、「◯◯(手法名)の中心値が0円のため、倍率での分解ができず金額差での表示になっています。0円になるのは◯◯だからです(D-08の理由文を共用)」のように理由まで書く。
  4. 「幅が違う理由」カードの冒頭に1行:「上の『差が生じる理由』は中心値の違い、この表はレンジ幅(P5〜P95)の広さの違いを分解したものです」。
- **対象:** `app/valuation/page.tsx`、`app/components/charts/Waterfall.tsx`

### 指示 D-08 【P1】試算の幅の「0円」に理由を付ける

- IFVIサブ係数等で中心値0の手法がある。0の行は非表示にせず(ユーザー了承済み)、値の隣に「なぜ0か」の短い注記を付ける(例: 「対象地域では当該係数が0のため」)。**理由は `packages/core` のプラグイン実装・除外事項リスト・docs/data のノートを確認し、事実に基づいて書く。**確認できない場合は「この手法では当該地点の係数が0と評価されています」に留める(推測で理由を作らない)。
- **対象:** `app/valuation/page.tsx`(手法一覧・フットボール)

### 指示 D-09 【P1】縦リズムの監査(/valuation・/financial-bridge)

- 「投資判断に使う代表値の選択」カードの上部余白がない(直前の交換/厚生価値グループの2カラムが `.card` ではない素の `div` のため `.card + .card` のマージン規則が効いていない)。同種の「素のdivとCardの隣接」を両ページで洗い出し、`.grid-2`/カスタムブロックにも下マージンが付くようCSSを整える(場当たりのinline styleではなくクラスで)。スクリーンショット2枚目の④のカード内パディング不足(ウォーターフォール周り・期待損失カード)も同時に確認・修正。

### 指示 D-11 【P0】④⑤の画面構成を「サマリー先・詳細は要求時」に再設計

- **現象:** ④は「拠点ごとの詳細カード群を全部並べ→最下部に重要な論点(やるべきこと)」、⑤も同構造で最下部に「この画面でやること」。ユーザーは毎回最下部までスクロールを強制され、拠点・課題が増えると成立しない。
- **修正(両ページ共通の型):**
  1. **頭出しバナー(全6画面共通):** C-03でStepNavに入れた「この画面でやること」を、**画面ヘッダー直下の細いバナー**にも表示する(残タスクがある時のみ。各項目はページ内の該当箇所やカードへのアンカーリンク)。StepNav側は前後リンク+完了表示のみに簡素化してよい。
  2. **④の構成:** ヘッダー → 頭出しバナー → 企業全体の財務データ(D-10)→ **拠点サマリーテーブル**(1拠点1行: 拠点名/調整幅(営業利益比)/自然債務/減損テスト判定/重要な論点の有無 → 行から詳細へ)→ 拠点別詳細(折りたたみ `details.collapse` か、サマリー行クリックで展開。既定は最重要拠点のみ展開)。「重要な論点」カードはサマリーテーブルの直後(上部)へ移動。
  3. **⑤の構成:** ヘッダー → 頭出しバナー → **拠点サマリーテーブル**(拠点/判定/選択中の対策/反映先/残タスク)→ 拠点別詳細(同上)。判定件数カードは移設済み(/ledger)のまま。
  4. 拠点別詳細の中身(既存カード群)は再利用し、並び順は現行(判定結果先頭等)を維持する。
- **対象:** `app/financial-bridge/page.tsx`、`app/decision/page.tsx`、`app/components/`(頭出しバナー共通化)、全画面(バナー適用)

## §E /decision(P1)

### 指示 D-13 【P1】「またぐ/またがない」の意味を画面で説明する

- 判定タグの直後に、判定別の含意を一文で常設表示する(C-06の意味文を拡張):
  - またがない: 「自然関連コストを織り込んでも投資判断の結論は変わらない、と確定できました。この課題の追加調査は不要です」
  - またぐ: 「自然関連コストを織り込むと、承認基準を上回るか下回るかが変わる可能性があります。結論を確定するには、レンジを支配する前提の詳細調査が必要です」
  - 保留: 既存文言(閾値入力の案内)
- **注意:** PRISMは投資可否そのものを断定しない規律(構想書)。「投資して良い」とは書かず、「結論(判定)が変わるか」の言い回しに徹する。ガイドにもこの3値の読み方を追記。
- **対象:** `app/decision/page.tsx`、`app/components/labels.ts`

### 指示 D-14 【P1】対策案の比較グラフの再検討

- **現象:** 散布図の点が軸上に張り付き、比較として機能していない。
- **修正(この順で):**
  1. まず散布図の実装を疑う: 軸レンジに余白(パディング)を持たせ、原点張り付き・ラベル重なりを解消する。0値の候補(投資額0の「何もしない」等)は原点ではなく軸内に収まるようスケールを調整。
  2. その上で2軸散布図が比較として意味を持つか判断する。候補数が3〜4件で2軸(財務効果×環境効果)の意図(構想書M6の2軸比較)は正当なので**散布図は残す**方針とし、表(既存)を主、散布図を副とする配置は維持。
  3. 1で解決しない場合のみ、`lib/demo/company.ts` の対策ダミーデータの数値を調整して点がグラフ内に分布するようにする(**テスト416件を壊さないこと**。値をアサートしているテストがあれば、demo層のテストに限り期待値を更新してよい。`packages/core` のテストは触らない)。
- **対象:** `app/components/charts/Scatter.tssx`→`Scatter.tsx`、`app/decision/page.tsx`、(必要時のみ)`lib/demo/company.ts`
