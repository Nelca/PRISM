# PRISM UI/UX修正指示書

**作成日:** 2026-08-16
**対象:** 現行Webアプリ(ホーム+9画面、M1〜M8パイプラインUI)。ドキュメント一式(concept-v2、要件定義M1〜M8、demo-guide、mvp-completion-gap、design-rationale-log ほか)と `app/` 配下の全画面コードを突き合わせてレビューした結果に基づく修正指示。
**想定ユーザー:** 非財務情報の知識はあるが、M&A・デューデリジェンス(DD)の知識は浅い(サステナ/IR担当を典型とする)初見の利用者。
**優先度:** P0=迷いを直接生む / P1=理解を大きく助ける / P2=磨き込み
**スコープ:** 本指示書はUI/UX(情報設計・文言・導線)のみを対象とし、`packages/core` の計算ロジック・型ガードには変更を要求しない。

---

## §0 総評

計算ロジックと「見せてはいけないものを見せない」規律(価値概念の分離、推奨値を出さない、理由必須)は構想書どおり高い水準で実装されている。問題は**情報設計がモジュール(M1〜M8)単位のままユーザーに露出している**ことに集約される。具体的には次の3点。

1. **構造:** 本来一本道のパイプラインが9画面に分かれ、うち2組(取込/拠点、算定/比較)は内容が重複している。初見では「どこから始めて、次にどこへ行くのか」が分からない。
2. **言葉:** `crosses`・`weak_reference`・`mi-xxx`・GapFinding ID など内部表現がそのまま画面に出る箇所が残っており、DDの語彙(エクスポージャ、拘束方式、ティア等)が翻訳なしで使われている。
3. **ゴールへの接続:** 「財務評価が適切に行えたか」を担保する必須操作(代表値の選択・承認閾値の入力・反映先の決定)が各画面に散らばり、「新たな発見」(手法間の差の原因、減損前提への抵触、開示根拠の欠落)が深い階層に埋まっている。

以下、§1 画面構成(P0)→ §2 言葉と数値(P0〜P1)→ §3 導線(P1)→ §4 ゴールへの接続(P0〜P1)の順に指示する。§5は「壊してはいけない現状の良い点」、§6は実施順序。

### 指示 01 【P0】ナビは静かに保ち、順序の誘導は「状態表示」と「文脈導線」で行う

- **現状:** サイドナビが「対象の把握/価値の算定と判断/開示と記録」の3グループ・9項目。順序性が視覚化されておらず、初見ではどこから始めるか判断できない。ホームの案内も「左のナビゲーションから各モジュールへ」のみ。
- **方針:** 番号付きの常設ステッパーは採らない。番号やチェックマークが常時見える装飾は、初回にしか情報価値がなく、**複数年・毎四半期の反復利用では視覚ノイズに転じる**ため。ナビ本体は「毎日使う道具」として静かに保ち、順序の学習は初見時にだけ効く別の層で担う。
- **修正:** 次の4点に分解して実装する。
  1. **並び順と見出し:** ナビ項目を提案図の業務順に並べ替え、グループ見出しを動詞ラベル(「評価する/判断する/開示する」)にする。番号は振らない。順序は並びと見出しだけで暗黙に伝える。
  2. **工程図はホームに限定:** 6ステップの工程表示(どこまで進んだか)はホームの進捗ブロック(指示04)にのみ置く。常設クロームには出さない。
  3. **文脈導線:** 各画面の末尾に「次:財務への影響 →」のような前後リンクを置く。初見者には道しるべ、常連には単なる移動手段として働き、どちらにもノイズにならない。
  4. **状態表示は「要対応のときだけ」:** ナビ項目には、未完了の必須判断(指示13の共通関数から導出)がある画面にだけ小さなドットを表示する。**完了マークは常時表示しない**——「済」の常時表示は運用が回り始めた2年目以降、全項目が済になって無意味化する。信号があるときだけ光る設計とする。
- **対象:** `app/components/nav.tsx`、要対応判定は指示13の `lib/pipeline/open-tasks.ts`(新設)を共用

### 指示 02 【P0】「データの取込」と「対象定義とLocate」を1画面に統合する

- **現状:** 両画面が「拠点一覧」と「取込エラー(ingestionErrors)」を二重に表示している(`intake/page.tsx:29-63` と `sites/page.tsx:29-73`)。ユーザーから見ればどちらも「対象を登録する」作業であり、分ける理由(実装がCSV経路と手入力経路で分かれている)はユーザーの関心ではない。
- **修正:** 「① データと拠点」1画面に統合。上段=登録手段(CSV3ファイル一括/1件ずつ追加をタブで並置)、中段=拠点一覧+座標解決状態、下段=取込時に除外された行(理由付き)。感応度スコア上位の表は②の冒頭に移す(絞り込みの入力なので②の文脈が正しい)。ナビ名から「Locate」(TNFD用語)を外し、「データと拠点の登録」とする。
- **あわせて:** intake画面のガイド文が `docs/data-intake-guide.md` というリポジトリ内パスを案内している(`intake/page.tsx:18`)。非エンジニアには辿れないため、記入テンプレート(`lib/intake/templates/`)を画面からダウンロードできるリンクに置き換え、記入者(顧客IR/PRISM運用チーム/財務部門)を表組みで画面内に示す。
- **対象:** `app/intake/page.tsx`、`app/sites/page.tsx`、`app/sites/add-site-form.tsx`(業種入力の placeholder「例: chemicals」は日本語選択式に)

### 指示 03 【P0】「価値の算定」と「算定結果の比較」を1画面に統合する

- **現状:** 同一のValuationRecord群に対し、/valuationと/decompositionが同じフットボールチャートを二度描画し(`valuation/page.tsx:134`、`decomposition/page.tsx:139`)、METHOD_LABEL定数も両ファイルに重複定義されている。ユーザーの実際のタスクは「複数の算定結果を見る→差の理由を理解する→代表値を選ぶ」という一続きであり、画面を分けると「比較のためにもう一度同じ図を見る」体験になる。
- **修正:** 「③ 価値の算定と代表値の選択」1画面に統合し、上から次の順に並べる:(1)算定対象と手法一覧表 →(2)フットボールチャート(1回だけ)→(3)差が生じる理由(ウォーターフォール+読み下し文)→(4)幅が違う理由 →(5)**代表値の選択(この画面の出口=必須アクション)**→(6)前年度手法との比較。トルネード図(試算の幅に影響する要因)と除外項目は折りたたみ(「詳しく見る」)に格下げする。METHOD_LABELは共通定数へ移動。
- **対象:** `app/valuation/page.tsx`、`app/decomposition/page.tsx`(統合)、METHOD_LABEL → `app/components/method-labels.ts`(新設)

### 指示 04 【P0】ホームを「現在地と次にやること」に作り替える

- **現状:** ホームは件数サマリーと、生値の混じった表(判定=`crosses`、対策=`selectedCountermeasureKey`の内部キー、`app/page.tsx:54,57`)のみ。初見ユーザーが最初に見る画面なのに、何をすべきか・何が分かったのかを伝えていない。
- **修正:** 3ブロック構成にする。**(a)進捗:** 6ステップの工程図と完了状態。指示01の方針どおり、工程の可視化は常設ナビではなく**この画面だけ**が担う(判定ロジックは指示13の共通関数を再利用)。**(b)次にやること:** 未完了の必須判断のチェックリスト(指示13)。**(c)分かったこと:** 発見サマリー(指示14)。M6/M8の表・件数はそれぞれ⑤と記録画面に任せ、ホームからは撤去する。
- **対象:** `app/page.tsx`

### 指示 05 【P1】「変更履歴」(/ledger)を業務フローの外の「記録」画面に整理する

- **現状:** 画面の先頭がRecalculationHashのカードで、ハッシュとIDの表が大半を占める。監査対応には必要だが、日常業務の画面としては全て読めない・読む必要がない。また従量課金の明細(判定件数)が⑤対策の検討の末尾に同居している(`decision/page.tsx:227-262`)。
- **修正:** (1)画面名を「記録(監査証跡)」とし、ナビのステップ列の外(下部)に置く。(2)先頭を人が読める2表(変更履歴=誰がいつ何を選んだか/係数・パラメータの版)にし、ハッシュ類は「技術的な検証情報」として折りたたむ。(3)判定件数(課金根拠)カードは⑤から本画面(または将来の契約管理画面)へ移す。意思決定の最中に課金明細が見えるのは、判断を歪めうるノイズ。
- **対象:** `app/ledger/page.tsx`、`app/decision/page.tsx`

### 指示 07 【P1】用語を統一し、DD由来の語に一行の説明を付ける

- **現状:** 同じ概念に複数の言い方が混在:「深掘り/深掘り評価/詳細評価/要詳細評価」「スクリーニング/概算評価」「拘束方式/反映先」。またDD・ファイナンス語彙(エクスポージャ、適合度ティア、非GAAP指標、NPV)が説明なしで使われる。想定ユーザーはM&A/DDの知識が浅いという前提に反する。
- **修正:** 下表のとおり正とする語を決め、全画面・ナビ・ガイド文を置換する。初出箇所には点線下線+ホバー/タップで一行説明(タイトル属性で可)を付ける。

  | 正とする語 | 置き換える語 | 初出時の一行説明(案) |
  |---|---|---|
  | 詳細評価 | 深掘り/深掘り評価/要詳細評価 | 確度の高いデータで再計算する追加評価。対象を絞って行う |
  | 概算評価 | スクリーニング | 全対象に行う簡易な評価 |
  | 結果の反映先 | 拘束方式 | この判定結果を社内のどの仕組みに組み込むか |
  | 影響しうる財務規模 | 財務エクスポージャ | この課題が影響しうる売上・費用の大きさ |
  | 感応度(自然との関わりの強さ) | 感応度スコア | TNFDの5基準のうち該当した数。分母は評価できた基準数 |
  | 算定の確からしさ(A/B/C) | 適合度ティア | A=現地評価に近い/B=補正付きで実務利用可/C=桁の把握のみ |
  | 投資対効果(NPV) | 自然調整後NPV(単独表記) | 自然関連のコスト・便益を加味した正味現在価値 |

  ValuationRecord・DecisionRecord・AssumptionEntryなどのオブジェクト名は本文に出さず、「算定結果」「判定の記録」「前提の記録」と言い換える(空状態メッセージ「対象となる交換価値ValuationRecordがありません」等も対象。`decision/page.tsx:40`、`financial-bridge/page.tsx:22`、`app/page.tsx:63`)。「非GAAP指標」ラベルは規律上残すが、初出に「監査済み財務諸表の数値ではありません」の説明を添える。
- **対象:** 全画面+`docs/demo-guide.md`(§4が旧画面構成のまま。統合後に全面改訂)

### 指示 08 【P1】無次元スコアを「順位と相対値」に翻訳する

- **現状:** ②の表に「不確実性 0.412」「優先度 0.842」のような正規化スコアが小数3桁で並ぶ(`assessment/page.tsx:74-82`)。初見ユーザーにはこの数字の大小が判断できず、「なぜこの課題だけ詳細評価なのか」が読み取れない。

## §3 導線 — 初見でも迷わず一周できるようにする

### 指示 10 【P1】画面ガイドを「隠す」から「初回は見せる」に変える

### 指示 11 【P1】空状態に「原因と次の一手」を必ず付ける

## §4 最終ゴールへの接続 — 「適切な財務評価」と「新たな発見」を体験の出口にする

### 指示 13 【P0】必須の人間判断を「未完了タスク」として一元表示する

- **現状:** 財務評価が「適切」であるためにユーザー自身が行うべき判断——代表値の選択(③)、承認閾値の入力(⑤)、結果の反映先の決定(⑤)、開示ギャップへの対応(⑥)——が各画面に散らばっている。④の「重要な論点」カードがこれを部分的に集約しているが、フロー途中の画面にあるため、そこに到達する前のユーザーには見えない。
- **修正:** ④のレッドフラグ導出ロジック(`financial-bridge/page.tsx:29-83`)を共通関数(例:`lib/pipeline/open-tasks.ts`)に切り出し、**ホームの「次にやること」チェックリスト**として表示する(指示04の(b))。各項目は該当画面の該当カードへ直接リンクする。④の「重要な論点」カードはこの共通関数を参照する形で存置してよい。「閾値未入力なら判定は保留・仮の値を置かない」という現仕様は正しいので、チェックリストでは「承認閾値が未入力のため判定が保留中です(財務・経営企画部門への確認が必要)」と**誰に聞くべきか**まで書く。
- **対象:** `app/financial-bridge/page.tsx`、`app/page.tsx`、`lib/pipeline/`(新設共通関数)

### 指示 14 【P0】「分かったこと(発見)」をホームに平易な文で掲出する

- **現状:** このプロダクトが約束する発見——「手法間で最大N倍の差があり、その主因は測っている範囲の違い」「自然債務が減損テストの前提に抵触」「開示文言に根拠が不足」「判定が承認基準をまたぐ/またがない」——はすべて算出済みだが、③④⑤⑥の深い位置に分散しており、一周し終えたユーザーにも全体像が残らない。
- **修正:** ホームに「分かったこと」ブロックを設け、実データから導出した発見を**結論から書いた一文カード**で並べる。例:
  - 「本社工場の水リスクは、算定方法により**年◯億〜◯億円**と幅がある。差の主因は**測っている範囲の違い**で、精度の問題ではない → ③で詳細」
  - 「選択中の対策込みでも、投資判断の承認基準を**またがない**=この論点は今回の投資判断を変えない → ⑤で詳細」
  - 「自然債務◯億円は、減損テストの前提の**見直しが必要な水準** → ④で詳細」

  文言はテンプレート+数値の機械的埋め込みで生成し(M7の下書きと同じ方針)、断定調は判定結果(verdict等)の事実の範囲に限る。「またがない=効かないと確定できた」も価値である、というconcept-v2の中核メッセージをここで言語化する。
- **対象:** `app/page.tsx`、導出は指示13の共通関数と同居可

### 指示 15 【P1】⑤の画面順序を「判定が主役」に組み替える

- **現状:** ⑤は散布図(対策案の比較)が先頭にあり、プロダクトの価値の中心である★判定(承認基準をまたぐか)が3番目のカードに沈んでいる。散布図の軸ラベルも専門的(指示09)。
- **修正:** 拠点ごとの表示順を(1)判定結果(大きく:「承認基準をまたがない」+その意味の一文「自然関連コストを織り込んでも、この投資の結論は変わりません」)→(2)対策案の比較(表→散布図の順)→(3)結果の反映先、に組み替える。「前提が変わった判定」アラートは判定結果カードの直下へ移し、見落とさない位置にする。
- **対象:** `app/decision/page.tsx`
