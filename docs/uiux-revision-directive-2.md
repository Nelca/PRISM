# PRISM UI/UX修正指示書 第2版(ディテール改善)

**作成日:** 2026-08-16
**位置づけ:** `uiux-revision-directive.md`(第1版・実施済み)の後続。実施後の実画面(スクリーンショット3枚: /sites 上下・/assessment)とコードを突き合わせた、SaaSプロダクトデザイナー観点のディテールレビューに基づく修正指示。
**優先度:** P0=機能・理解の欠落 / P1=明確な視覚不良 / P2=磨き込み
**制約(第1版から継続):** `packages/core` 不変。第1版§5「維持すべき点」を壊さない。git commitしない。

---

## §0 総評

第1版で情報設計(画面統合・用語・導線)は改善されたが、**コンポーネントレベルの品質**が追いついていない。今回の問題は4系統:

1. **レイアウトの構造欠陥:** ページタイトルが縦に折り返す(全画面共通の構造問題)
2. **アフォーダンスの欠如:** 切り替えられるもの(評価の深さ)がそう見えず、編集できるべきもの(拠点)に操作が存在しない
3. **内部語の漏れ残り:** coreが生成する理由文(`normalizedScore=2.000`・「深掘り評価」)がそのまま画面に出る
4. **ディテールの粗さ:** ボタン文字の縦折れ、バーが読めない、ネイティブfile input、空状態の過剰な存在感

---

## §1 P0 — 機能・理解の欠落

### 指示 B-01 【P0】ページタイトルの縦折れを解消する(全画面共通の構造修正)

- **現象:** /sites のタイトルが「データと/拠点の登/録」と3行に折り返している(スクリーンショット2枚目)。
- **根本原因:** `app/components/ui.tsx` の `Guide` が「iボタン」と「開いたガイドボックス」を同じフラグメントで返し、それが `.screen__title-row`(`display:flex`)の子として展開される。ガイドが開くと(第1版指示10で初回は開く仕様にしたため初見時に必ず)ボックスがタイトルと**同じ行**に入り、h1が数文字幅まで圧縮される。
- **修正:**
  1. 構造を分離する。`.screen__title-row` には h1+iボタンのみ。ガイドボックスは行の**外**(ScreenLeadの下)に全幅で描画する。`Guide` をトリガーとボックスに分けるか、`screen__head` 全体を1コンポーネント(例 `ScreenHeader`)に統合して title / lead / guide の順で縦に積む。全ページの呼び出し箇所を統一的に置き換える。
  2. `.screen__title` に `text-wrap: balance` と、折返し時も語中で割れないよう `word-break: keep-all` を付与(「価値の算定と代表値の選択」のような長タイトルが狭幅で折れる場合も語単位で折れるように)。
- **対象:** `app/components/ui.tsx`、`app/globals.css`、全page.tsxの`screen__head`部

### 指示 B-02 【P0】評価の深さ切替をセグメントコントロールにする

- **現象:** /assessment の「状態」列の「概算評価/詳細評価」が、(1)ボタンに見えない・切り替えられると分からない、(2)セル幅不足で「概算評/価」と縦折れ、(3)非選択側が単なるラベルに見える(スクリーンショット3枚目)。
- **修正:**
  1. `.seg-control` を新設(`app/globals.css`): 2つの選択肢が**結合された**1つのコントロール(外枠1本・中仕切り・選択側は`--accent`塗り+白字・非選択側はhoverで反応)。`white-space: nowrap`・`cursor: pointer`。`DepthToggle` をこれに載せ替え、ボタンに `aria-pressed` を付与。
  2. 送信中(`pending`)は選択中の側に「…」等の処理中表示を出し、二度押しを防ぐ(現状はopacityのみ)。
  3. 列見出し「状態」→「評価の深さ」。カードの `foot` に「評価の深さはクリックで切り替えられます。切り替えは記録に残ります」を追記。
  4. 同じアフォーダンス原則(選択状態が塗りで示され、非選択側がクリック可能に見える)を、③の `RepresentativeSelector`・⑤の `CountermeasureSelector` にも点検適用する(必要な場合のみ。モーダルを開くトリガーはボタンのままでよい)。
- **対象:** `app/assessment/depth-toggle.tsx`、`app/assessment/page.tsx`、`app/globals.css`、(点検)`app/valuation/representative-selector.tsx`・`app/decision/countermeasure-selector.tsx`

### 指示 B-03 【P0】拠点の編集・削除を実装する(できない行には理由を示す)

- **現象:** /sites の拠点一覧に操作が一切なく、登録した拠点を修正できない。修正できない理由の表示もない(スクリーンショット1枚目)。
- **実装調査の結果(前提知識):**
  - `site` テーブルは追記専用ロールの**唯一の例外**としてUPDATE/DELETEが許可されている(`0001_append_only_role.sql`、取込やり直しのため)。設計上、編集・削除は禁止されていない。
  - `lib/db/repositories/sites.ts` には `addSiteEntry`/`replaceSiteEntries` のみ存在し、update/removeが未実装。
  - 一覧に表示される拠点のうち **site-042等のデモ既定拠点は `lib/demo/company.ts` の固定データでDBに存在しない**(パイプラインが `userSites`(DB)とマージする)。これらはDB操作では編集できない。
- **修正:**
  1. `lib/db/repositories/sites.ts` に `updateSiteEntry(tenantId, id, row, deepDive)` と `removeSiteEntry(tenantId, id)` を追加(`site-user-*` のみ対象)。
  2. 拠点一覧に「操作」列を追加。**ユーザー登録拠点**(`site-user-*`)には「編集」「削除」。編集は既存 `add-site-form.tsx` のモーダルを流用し、既存値をプリフィル(フォームを追加/編集両対応に汎用化)。削除は確認ダイアログ付き(「過去の計算結果・監査証跡は消えません」と明記)。
  3. **デモ既定拠点**には「デモ既定」タグを表示し、編集・削除ボタンは置かない代わりに、操作列に淡色で「編集不可」+title「架空企業のデモ既定拠点のため編集できません」。**何も出さずに放置しない**(今回の指摘の本質は「できないことが分からない」こと)。
  4. 編集・削除後は `executeAndPersistRun` で新しいrunを作成し、`REVALIDATE_PATHS` を無効化(addSiteActionと同じ流儀)。
  5. 編集・削除を監査証跡に残す。`appendInteractionEvent` の既存のイベント型を確認し、対応できる形(kind・payload)で記録する。型の制約上むずかしければ、その旨と代替(actionLogに出る別経路)を報告に書く。
- **対象:** `lib/db/repositories/sites.ts`、`app/sites/actions.ts`、`app/sites/add-site-form.tsx`(汎用化)、`app/sites/page.tsx`
- **将来課題(今回やらない):** デモ既定拠点そのものの編集は、固定データのDB化(シード方式への変更)が必要。実データ運用の設計と絡むため本指示のスコープ外とし、記録のみ。

### 指示 B-04 【P0】coreの理由文の内部語をUI側で翻訳する

- **現象:** /assessment の判定列に「優先度算定の結果(normalizedScore=2.000)が上位20%に入らなかったため、深掘り評価には進みません。」「優先度算定では深掘り対象だったが、手動で概算評価に戻された。」がそのまま表示される。`normalizedScore` は内部変数名、「深掘り」は第1版指示07で廃止した用語、文体も不統一(スクリーンショット3枚目)。
- **修正:** `packages/core` は変更せず、UI側に理由文の整形関数(例: `formatDepthReason`、`app/components/labels.ts` に同居可)を作る。既知パターンを正規表現で解析し、**実データの数値を使って**平易文に組み替える:
  - `優先度算定の結果(normalizedScore=X)が上位Y%に入らなかったため、深掘り評価には進みません。` → `優先度が上位Y%に入らなかったため、概算評価に留まっています(スコア X)。`
  - `…深掘り対象だったが、手動で概算評価に戻された。` → `優先度算定では詳細評価の対象でしたが、手動で概算評価に戻されています。`
  - 未知のパターンは原文をそのまま表示(壊さない)。ただし「深掘り」→「詳細評価」の語置換だけは常に適用してよい。
  - 文体はです・ます調に統一。
- **対象:** `app/components/labels.ts`(整形関数)、`app/assessment/page.tsx`。ほかの画面でcore由来の文をそのまま出している箇所(`exclusionReason`・`unavailableReason`・`notDecomposedReason` 等)も grep で点検し、内部語が漏れているものがあれば同様に処置。

## §2 P1 — 明確な視覚不良

### 指示 B-05 【P1】優先度の内訳バーを読めるようにする

- **現象:** 内訳4列のバー(`.pbar__fill--sub`)が薄すぎて差が読めない。数値の手がかりがhover(title)にしかない。ヘッダー「開示必須性」が「開示必須/性」と縦折れ(スクリーンショット3枚目)。
- **修正:**
  1. `--sub` の色を濃く(accentの中間トーン。`--accent-line` は薄すぎる)。
  2. 各バーの右に百分位の短い数値(0〜100の整数、例「83」)を小書きのモノスペースで常時表示。titleの詳細(生値)は維持。
  3. `table.data-table th` に `white-space: nowrap` を追加し、内訳ヘッダーは「感応度/財務/不確実性/開示」に短縮(フルネームと説明はtitleへ)。
  4. 「判定」列見出しは「理由」に変更(B-04と整合)。
- **対象:** `app/assessment/page.tsx`、`app/globals.css`

### 指示 B-06 【P1】座標解決列をステータスタグにし、編集導線につなぐ

- **現象:** /sites の座標解決列が「座標あり/住所→座標解決済み/未解決」の素テキスト。「未解決」の帰結(評価対象外になる)がその場で分からない(スクリーンショット1枚目)。
- **修正:** Tag化する。「座標あり」「住所→解決済み」=neutral、「未解決」=warn+title「座標が解決できないため評価対象外になります」。未解決かつユーザー登録拠点の行では、B-03の「編集」で修正できることを示す(warn タグの直後に編集への誘導、または操作列との視覚的関連付け)。
- **対象:** `app/sites/page.tsx`

### 指示 B-07 【P1】ボタン・ラベルの縦折れを全体で禁止する

- **現象:** 「記入例をダウンロ/ード」(スクリーンショット2枚目)、「概算評/価」(B-02)。ボタン内改行は常に事故。
- **修正:** `.pill-btn` に `white-space: nowrap` を追加(全ボタンに効かせる)。その上で各所の幅が破綻しないか確認し、「記入するファイルと担当」のテンプレート列はラベルを「記入例」に短縮(download属性・title維持)。
- **対象:** `app/globals.css`、`app/sites/page.tsx`

### 指示 B-08 【P1】ファイル入力をデザインシステムに載せる

- **現象:** CSV取込の3つの入力がブラウザ標準の「ファイルを選択 選択されていません」のまま(スクリーンショット2枚目)。
- **修正:** カスタムfile入力コンポーネントを作る(`input[type=file]` は視覚的に隠し、`label` をpill-btn風の「ファイルを選ぶ」+選択済みファイル名の表示領域に。未選択時は「未選択」)。キーボード操作・フォーカスリングを維持(inputを`display:none`にせず視覚的隠蔽にする等、アクセシブルな定石で)。3入力すべてに適用。
- **対象:** `app/sites/import-form.tsx`、`app/components/ui.tsx`(汎用化する場合)、`app/globals.css`

## §3 P2 — 磨き込み

### 指示 B-09 【P2】空状態カードの存在感を下げる

- **現象:** 「取込時に除外された行 0件」カードが、0件でも本文+注記で大きな面積を占める(スクリーンショット1枚目)。
- **修正:** 0件のときは1行のコンパクト表示(見出し+「0件 — 除外された行はありません」)にし、注記(「座標も住所もない拠点は…」)は0件時には出さない(1件以上のときのみ表示)。カード自体は残す(「黙って消えない」原則の維持)。
- **対象:** `app/sites/page.tsx`

### 指示 B-10 【P2】文言・トーンの細部

1. 「記入するファイルと担当」の記入者列「顧客の財務部門への確認が必要」は担当名ではない。「顧客の財務部門」+補足小書き「(確認が必要)」に分離。
2. 「感応度が高い拠点」表の「詳細評価」タグが warn(赤系)。赤は警告・危険専用とし、accent系のタグに変更(詳細評価は良い状態でも悪い状態でもない)。
3. です・ます調への統一を全画面で最終確認(B-04と重複しない範囲。例: `foot` 文の「〜とは限らない」→「〜とは限りません」)。
- **対象:** `app/sites/page.tsx`、`app/assessment/page.tsx`、各page.tsxのfoot文

### 指示 B-11 【P2】全画面の一貫性最終チェック

1. B-01適用後、長タイトル(「価値の算定と代表値の選択」等)が全画面で1行に収まるか、折れる場合も語単位で折れるかを確認。
2. `table.data-table th` の `text-transform: uppercase` は日本語見出しには無意味なので削除(英字が残る列があれば個別対応)。
3. トグル・選択UI(B-02のセグメント、選択中タグ、ラジオ風選択)の見た目が画面間で揃っているか確認し、乖離があれば `.seg-control`/既存Tagパターンに寄せる。
- **対象:** 全page.tsx、`app/globals.css`

## §4 実施順序と検証

| 波 | 指示 | 担当の目安 |
|---|---|---|
| **第A波** | B-03(拠点の編集・削除 — DB層+Server Action+モーダル汎用化) | 機能実装(重) |
| **第B波** | B-01・B-02・B-04(P0残り)→ B-05〜B-08(P1)→ B-09〜B-11(P2) | UI層の集中修正 |

- 各波の完了条件: `npm run typecheck` / `npm run lint` / `npm test` 全通過。
- 開発サーバーが localhost:3000 で動作中の場合がある。**再起動・停止はせず**、確認は読み取り(GET)のみで行うこと。書き込み系の動作確認はテストで担保する。
- **受け入れ基準(第2版):** (1) 全画面でタイトルが正常に1行表示される、(2) 評価の深さが切り替えられることが見た目で分かり、ボタン内改行がゼロ、(3) ユーザー登録拠点が編集・削除でき、デモ既定拠点は編集できない理由が表示される、(4) 画面上に `normalizedScore` 等の内部変数名・「深掘り」の残存がゼロ。
